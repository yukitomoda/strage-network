# Storage Network 設計ドキュメント

Bedrock版Minecraft向けの倉庫（ストレージネットワーク）アドオン。個人利用のため、バージョン互換性やクラフトバランスは考慮しない。UXのためなら将来のアップデートで壊れうる手法（JSON UIのバニラ画面上書きなど）も許容する。Scripting API (`@minecraft/server` / `@minecraft/server-ui`) を使用し、実験的機能も許容する。

## 1. 概要

「コントローラ」「ターミナル」「接続ツール（レンチ）」の3つを導入する。

- **コントローラ**: 倉庫ネットワークにつき1つ。ネットワークの引き出し処理を実行する。
- **ターミナル**: 倉庫ネットワークへの引き出しUIを開くブロック。自身は状態を持たず、引き出しされたアイテムは設置面に応じて張り付いた先(6方向のいずれか)のストレージへ直接搬入される。1ネットワークに複数接続可能。詳細は6章参照。
- **ストレージ**: アイテムの実体を保管する場所。**専用ブロックは作らず、`minecraft:inventory`を持つバニラのコンテナブロック（チェスト・樽・シュルカーボックス等）をそのまま使う**。
- **接続ツール（レンチ）**: コントローラ・ストレージ・ターミナルをネットワークに接続/切断するためのアイテム。将来的には汎用設定ツールに拡張予定だが、MVPではネットワーク構築専用。

1ワールド内に複数の独立したネットワーク（＝複数のコントローラ）を同時に存在させられる。ネットワークの接続範囲は**同一ディメンション内に限定**する。

## 2. データモデルと永続化

Bedrock Scripting APIでは、ブロック単位の永続データを直接持てない（動的プロパティが使えるのは `World` / `Entity` / `ItemStack` のみ）。そのため、ネットワークの構造情報はすべて `world` の動的プロパティにJSON文字列として保存する。個人利用規模なので、一覧の線形走査で十分と判断し、逆引きインデックスは作らない。

```ts
// wh:network_ids -> string[]  (存在するネットワークIDの一覧)

// wh:network:<id> -> JSON
type NetworkData = {
  id: string;
  dimensionId: string;           // 同一ディメンション限定
  controller: Vector3;
  storages: Vector3[];
  terminals: Vector3[];
};

// wh:orders:<networkId> -> JSON (引き出しキュー, FIFO)
type OrderLine = {
  itemTypeId: string;
  itemName?: string;   // nameTag(銘)がある場合のみ。詳細は5章参照
  requested: number;
  delivered: number;   // これまでに実際に届けた数
  exhausted: boolean;  // 在庫不足/搬入先(ターミナルの張り付いた先)が満杯等で「これ以上は無理」と確定した
};
type Order = {
  id: string;           // 短い表示用ID(英数字4桁)。マルチプレイでの識別用途なので厳密な一意性は不要
  requestId: string;    // キャンセル指定用の厳密な一意ID(generateId()。表示には使わない。4章「キャンセル」参照)
  playerName: string;   // 完了通知の送り先を後から探すため(Entity.idはセッションをまたいで安定しない)
  terminal: Vector3;
  lines: OrderLine[];
};

// wh:issuing:<networkId> -> JSON (ターミナルからの発行待ちリスト。4章参照)
type IssuingEntry = {
  order: Order;          // lines は delivered=0, exhausted=false で初期化済み
  readyAtTick: number;   // 発行操作時の system.currentTick + ISSUE_DELAY_TICKS(MVPでは0)
};

// wh:order_cancels:<networkId> -> string[] (キャンセル対象のrequestId一覧。4章「キャンセル」参照)

// wh:partial:<networkId> -> JSON (部分成功/失敗の退避リスト)
type PartialResult = {
  orderId: string;
  terminal: Vector3;
  shortfall: { itemTypeId: string; itemName?: string; amount: number }[];
};
```

### ネットワークのライフサイクル

- コントローラブロックが設置された瞬間（`onPlace`相当）に新しいネットワークが自動生成され、自身が`controller`として登録される。
- コントローラが破壊されたら、ネットワークごと解体する（`storages`/`terminals`/`orders`/`issuing`/`order_cancels`/`partial`、および預け入れ・整理の同種のキュー`deposits`/`deposit_issuing`/`deposit_cancels`/`deposit_partial`/`organize`/`organize_cancels`もすべて削除。`network.ts`の`destroyNetwork`）。
- ストレージ・ターミナルが破壊された場合（`world.afterEvents.playerBreakBlock`）、破壊位置がいずれかのネットワークの`storages`/`terminals`と一致すればそのエントリを除去する。

## 3. 接続ツール（レンチ）

- カスタムアイテムコンポーネントの `onUseOn` でブロック右クリックを検知する。
- プレイヤーの「現在編集中のネットワークID」は `player.setDynamicProperty("wh:editing_network", id)` で保持する（EntityはDynamic Property使用可）。
- コントローラを**Shift+右クリック** → 編集モード開始（既に別ネットワークを編集中なら、そのネットワークに切り替える）。**同じネットワークを編集中に再度Shift+右クリックすると終了する**トグル動作。開始と終了で操作を分けず統一した方が分かりやすいという理由で、当初はShiftの有無を問わないトグル動作にしていたが、後述のモード切替式ツール化に伴い「コントローラの操作は常にShift+右クリック」に統一した（モードが増えてもコントローラの操作感だけは変わらないようにするため）。
- 編集モード中、ストレージ/ターミナルを右クリック → 接続済みなら切断、未接続なら接続(新規接続には範囲制限がある。後述)。
- **強調表示（MVP）**: `system.runInterval`で、`wh:editing_network`を持つプレイヤーがいれば、そのネットワークの`controller`/`storages`/`terminals`の座標にパーティクルを定期的にスポーンするだけの簡易実装。既知の課題として、パーティクル自体の寿命(1〜2秒)により切断直後も一瞬残る。修正案（自作の短寿命パーティクル、または`@minecraft/debug-utilities`の`DebugBox`）は10章参照。

### モード切替式ツールへの一般化(ネットワーク構築以外のメンテナンス操作の追加口)

ネットワーク構築以外のメンテナンス操作(Drain指定等)を今後も追加していく方針を決めた際、「用途ごとに別アイテムを実装する」か「1つのツールをモード切替で使い回す」かを検討し、**モード切替方式を採用した**。

- 理由: このアドオンには既に「プレイヤーごとの状態を動的プロパティで持つ」(`wh:editing_network`)仕組みと、DDUI(`CustomForm`)によるメニュー表示の仕組みが両方あり、モード切替はその延長で実装できる。別アイテム方式は個々の実装はシンプルだが、機能を増やすたびにBP/RPのアイテム定義・テクスチャ・lang登録一式が必要になり、ホットバーも圧迫する。
- **`onUse`(空中で使用)でモード選択メニューを開く**: `CustomForm`でモード一覧をボタン表示し、選んだモードを`player.setDynamicProperty("wh:tool_mode", mode)`に保存する(`toolMode.ts`/`toolModeUi.ts`)。デフォルトは`"build"`(従来のネットワーク構築モード)なので、このメニューを一度も開かなくても今までどおり使える。
- **メニューから編集モードを終了できる**: 編集モードの終了は本来コントローラをShift+右クリックする操作だが、コントローラから離れた場所にいると戻るのが面倒という要望を受け、このモード選択メニューにも同じ終了操作を追加した。編集中(`wh:editing_network`を持つ)の場合のみ、モード一覧の下に`divider`を挟んで「編集モードを終了する」ボタンを表示する(非編集中は何も追加されない)。`wh:editing_network`の読み書き(`getEditingNetworkId`/`setEditingNetworkId`)は元々`wrench.ts`内に閉じていたが、`toolModeUi.ts`からも参照する必要が生じたため、`toolMode.ts`と同じ考え方で`editingSession.ts`という専用モジュールに切り出した(`wrench.ts`は`toolModeUi.ts`をimportしているため、切り出さずに直接importすると循環importになる)。
- **`onUseOn`(ブロックに対して使用)は現在のモードで分岐する**: `"build"`ならストレージ/ターミナルの接続/切断処理、`"drain"`ならDrain指定のトグル処理(後述)。ただし**コントローラに対する操作(編集セッションの開始/終了)だけはモードに関係なく共通の処理**(`handleControllerUse`)で扱い、常にShift+右クリックで開始/終了する。「どのモードでもコントローラの操作感は同じにしたい」という要望を受けて、モード分岐より前にコントローラかどうかを判定するよう変更した。これに伴い、Drainモードでのストレージ操作も構築モードと同様に**事前にコントローラで編集セッションを開始しておく必要がある**ように変更した(以前は編集セッション不要でどのストレージにも直接Drain指定できたが、「セッションを開始/終了する操作はあるのに、開始してもしなくても挙動が変わらない」のは一貫性が無いと判断したため)。強調表示(後述)もこれに合わせて、Drainモードでは「編集中のネットワーク」のDrain指定ストレージだけを対象にするよう変更した(以前は全ネットワーク横断)。

**(実機で発見された不具合の修正済み)** 当初「`onUse`と`onUseOn`は排他的に呼び分けられる(ブロックを対象にした場合は`onUseOn`だけが発火する)」と想定していたが、実機では**`onUse`はブロックに対して使った場合も(`onUseOn`とは別に)発火する**ことが判明した。そのため何もせずブロックを右クリック/Shift+右クリックするたびにモード選択メニューが誤って開いてしまっていた。`onUse`側で`player.getBlockFromViewDirection({ maxDistance: 8 })`により視線の先のブロックをレイキャストし、ブロックが見つかった場合(=ブロックに対する使用だった場合、`onUseOn`が別途処理する)はメニューを開かないようにして回避した。距離はゲーム本来の到達距離と厳密に一致している必要はなく、「ブロック操作の右クリックでメニューが誤って開かない」ことだけが目的の緩い判定。

### ネットワークの接続範囲(コントローラを中心とした立方体、Tierに応じて可変)

当初、ストレージ/ターミナルの接続には距離の制限が一切無かった(ワールドのどこにあってもレンチで接続できた)。これを、**コントローラを中心とした一辺`2×range+1`の立方体の中**に制限した。当初は固定8マス(コントローラ自身のブロックを挟んで両側に8マスずつ=合計17マス四方、当初16マスで実装したが実機での確認を経て8マスに変更した)だったが、後述の「範囲」アップグレード軸の追加により**Tierに応じた可変値**(`controllerAxes.ts`の`getRangeForTier(tier)`、`[3, 4, 6, 9, 16]`)になった。

- **判定**(`network.ts`の`isWithinNetworkRange`): 当初は3次元ユークリッド距離(球)で判定していたが、(a) Minecraft本来の距離判定(ワールドボーダー等)は立方体状のものが多く感覚に合う、(b) 判定が`Math.abs(dx) <= R && ...`という単純な比較で済みsqrtが不要、(c) 後述の可視化がどの高さでも同じ大きさの断面になり単純化できる、という理由で立方体(各軸の距離が全てrange以内)に変更した。`network.ts`自体はアップグレード軸の仕組みを知らない(循環import回避、4章「グレード管理」参照)ため、`range`は呼び出し側(`wrench.ts`)が`getRangeForTier`で都度引いてから渡す。
- **適用箇所**: `wrench.ts`の`handleBuildModeUse`で、ストレージ/ターミナルを**新規接続**しようとした瞬間にのみチェックする。**切断は範囲外でも常に許可する**(この制限より前に接続済みだったメンバーが、後からこの制限が入ったことで切断すらできなくなる、という事故を避けるため)。範囲外だった場合は他の接続拒否ケース(二重登録防止、ターミナルの多重接続防止)と同じように、専用のメッセージ(「コントローラから各方向にNマスを超えているため接続できません。」)を出して`toggleStorage`/`toggleTerminal`を呼ばずに終了する。
- **既存ネットワークへの影響**: 過去にこの制限より遠くへ接続していたメンバーがいても、既存の接続自体はそのまま生きる(遡って強制切断はしない)。次に何か操作(再接続等)しようとした時に初めて制限がかかる。**ただし「範囲」アップグレード軸のTierダウンだけはこの方針の例外**(後述)。

#### 接続範囲の可視化(半透明の壁)

編集セッション中、接続可能な立方体の範囲を**半透明の板6枚(側面4枚+天面/底面)**で可視化する(`rangeIndicator.ts`)。

- **点(パーティクル)ではなく面にした経緯**: 当初はパーティクルで範囲の輪郭を描く案(コントローラの高さを基準に、上下1マスごとに輪切りの円/正方形を1本ずつ描く案)を検討したが、輪郭線だけでも点の数が数百〜千のオーダーになり負荷が心配だったこと、そもそも「点の集合」ではなく「塗りつぶした面」として見せたいという要望があったことから、方針を変えた。パーティクルには塗りつぶした平面という概念が無いため、代わりに**半透明のテクスチャを貼った薄い箱状のジオメトリを持つ非表示エンティティ**を使う。このアドオンには既に「非表示エンティティ+専用ジオメトリ+レンダーコントローラー」の仕組み(設定エンティティ等)と、アルファチャンネル対応のテクスチャ生成基盤(`tools/generate-placeholder-icon.mjs`)が揃っていたため、追加の技術リスクは小さかった。`@minecraft/debug-utilities`(プレビュー限定API、10章参照)のような、パック全体が通常版Minecraftで読み込めなくなるリスクがある手段には頼っていない。
- **ジオメトリ**(`RP/models/entity/range_wall.geo.json`/`range_ceiling.geo.json`): どちらも「真の2次元平面」ではなく「薄い箱」にしている(2次元平面はMinecraftのエンティティジオメトリでは片面しか描画されない=裏側から見ると透けて見えなくなるため、両面とも面を持つ薄い箱にすることでこの問題を回避した)。ジオメトリ自体は基準距離8.5マス(旧`NETWORK_RANGE_BLOCKS+0.5`相当)の1種類だけを持ち、Tierごとの実際のサイズは後述のスケールで表現する。
  - `range_wall`(側面用): エンティティのスポーン地点(ローカル原点=コントローラ中心)からローカルX方向に少し離れた位置に、Y方向・Z方向とも同じ距離だけ広がる板を1枚だけ持つ。4枚の壁は**全て同じスポーン地点(コントローラ中心)に、Yaw 0°/90°/180°/270°で回転させてスポーンする**ことで4方向をカバーする(ジオメトリ自体は1種類で済む)。
  - `range_ceiling`(天面/底面用): ローカルY=0を中心とした薄い板。天面/底面の使い分けは回転ではなく、**スポーン位置のYそのものをコントローラ中心から上下にずらす**ことで実現している(Y軸回転では上下方向の位置は変えられないため)。
  - テクスチャ(`RP/textures/entity/range_indicator.png`)は全面同じ半透明の水色(`[80,160,255,90]`)、マテリアルは半透明合成の`entity_alphablend`(既存の非表示エンティティが使う`entity_alphatest`は完全な不透明/透明の二値でグラデーションが無いため使えない)。
  - **境界のオフセットは`range`ちょうどではなく`+0.5`(`rangeIndicator.ts`の`rangeEdgeBlocks(tier)`)**: `isWithinNetworkRange`は「コントローラからブロック座標でrange以内」を接続可能とする(=そのブロック自体を含む)。壁をコントローラ中心からちょうど`range`の位置に置くと、範囲内最後のブロックのちょうど真ん中(ブロックは整数座標を起点に1マス分の幅を持つが、中心はそこから0.5マスずれた位置にある)を壁が横切ってしまい、そのブロックが範囲に含まれるのか分断されているのかが視覚的に紛らわしくなる不具合が実機で見つかった。境界ブロックの外側の面(=中心から`range+0.5`マス)に壁を置くことで、境界ブロックが範囲にきちんと含まれて見えるように修正した。
- **Tierごとのサイズ変更(`minecraft:scale`のcomponent_groups)**: 「範囲」アップグレード軸の追加に伴い、壁/天面のサイズがTierごとに変わる必要が生じた。エンティティのスケールは一様(X/Y/Z同じ倍率)にしか変更できない(`EntityScaleComponent`はスケール値を1つしか持たない)ため、**水平方向と垂直方向で別々の範囲を持たせる案は不採用にした**(意味シンボルの相談時にユーザーへ提示: 非対称にするとエンティティプロパティ+レンダーコントローラーのmolang配列参照+Tierごとに異なるジオメトリ生成という新技術一式が必要になり実装コスト・実機不具合リスクが大きく増えるため、水平の値に統一した)。水平=垂直であれば一様スケールだけでTierごとのサイズを正確に表現できる(壁ジオメトリのX方向オフセット・Y/Z方向の広がりは全て同じ基準距離8.5マスから作られているため、一様スケールで整合的に伸縮する)。`BP/entities/range_wall.json`・`range_ceiling.json`にTierごとの`minecraft:scale`を持つ`component_groups`を5つ用意し(スケール値=`(range+0.5)/8.5`)、`events`(`wh:set_range_tier0`〜`4`)でスポーン直後に1回だけ`entity.triggerEvent()`する(同一エンティティは生涯1つのTierしか持たないため、`remove`は不要)。天面/底面のYオフセット(スポーン位置そのもの)はスケールとは独立に、スクリプト側で`rangeEdgeBlocks(tier)`から直接計算する。
  - **既知の制約**: `SpawnEntityOptions`にスケールの初期値を指定する口が無いため、`triggerEvent`が反映されるまでの1〜2フレームだけ既定スケール(=スケール未指定、等倍)で描画される可能性がある(回転で見つかった現象と同種、後述の`initialRotation`参照)。半透明の一時的なインジケータであり実害は軽微なため、回避策は入れず既知の制約として記録するに留めている。
- **表示/非表示の同期**(`rangeIndicator.ts`の`syncRangeIndicator`): 参照カウントは持たず、呼ばれるたびに「表示されているべきか」を**都度再計算**して実際のエンティティの有無と一致させる(既存の設定エンティティの「無ければ作る」パターンと同じ考え方)。誰かが表示中かどうかの判定(`editingSession.ts`の`isAnyoneEditingNetwork`)は、複数人が同時に同じネットワークを編集していることもあるため、「自分が編集を終了した」だけでは即座に隠してよいか分からず、ログイン中の全プレイヤーを見て誰か1人でもまだ編集中なら表示を続ける。**「範囲」軸のTierが変わった場合の追従も同じ仕組みに乗せている**: 表示中のインジケータが記録しているスポーン時Tier(動的プロパティ`wh:owner_tier`)が現在のコントローラのTierと一致しなければ、一旦削除して現在Tierで再スポーンする。新たな即時同期は追加せず、既存の定期実行(次項)による都度収束に任せることで、編集セッション中にキットを付け替えた場合も最大`HIGHLIGHT_INTERVAL`(0.5秒)以内に表示が追従する。
- **編集セッション終了処理の一本化**(`editingSession.ts`の`endEditingSession`): インジケータの表示同期をし忘れるバグを防ぐため、`setEditingNetworkId(player, undefined)`を直接呼ぶのをやめ、同期処理も含めた`endEditingSession(player)`に一本化した。呼び出し元は4箇所: コントローラでの終了(`wrench.ts`の`handleControllerUse`)、レンチメニューからの終了(`toolModeUi.ts`、3章参照)、**プレイヤー退出時の強制終了**(`wrench.ts`の`registerWrenchPlayerLeaveWatcher`、`world.beforeEvents.playerLeave`)、そして**コントローラ破壊時の強制終了**(`controllerBlock.ts`の`onPlayerBreak`、次項)。
- **(実機で発見された不具合の修正済み) 編集中にコントローラを破壊すると範囲表示が壁として永久に残る**: 編集セッションを終了しないままコントローラを破壊すると、(a) プレイヤーの編集状態(`wh:editing_network`)が、もう存在しないネットワークIDを指したまま残ってしまい、(b) 範囲表示の壁/天面エンティティも片付けられずに残ってしまう不具合が実機で見つかった。原因は`reconcileAllRangeIndicators`(定期ループ)が`getAllNetworks()`(**現存する**ネットワーク一覧)を巡回して同期する仕組みのため、`destroyNetwork`でネットワークが解体され一覧から消えた瞬間、そのネットワークに紐づく壁エンティティはもう誰からも「片付け対象」として見つけてもらえなくなる、というものだった。対処として、`controllerBlock.ts`の`onPlayerBreak`で`destroyNetwork`を呼ぶ**前**に、そのネットワークを編集中の全プレイヤー(`world.getPlayers()`を`getEditingNetworkId(p) === network.id`で絞り込み)に対して`endEditingSession(p)`を呼ぶようにした。ネットワークがまだ存在するうちに終了処理を行うことで、`endEditingSession`内の`syncRangeIndicator`が正しくエンティティを削除でき、`wh:editing_network`も正しくクリアされる。破壊したプレイヤー自身が編集中だった場合はもちろん、(将来的にマルチプレイで)別のプレイヤーが編集中に誰かがそのコントローラを壊した場合もこの経路でカバーされる。
- **(実機で発見された不具合の修正済み) ログアウトしても壁が消えない**: 上記の`playerLeave`ベースの後片付けだけでは不十分だった。シングルプレイでワールドを終了する場合など、`beforeEvents.playerLeave`内の処理が完了するより先にワールド自体が終了してしまい、後片付け(エンティティ削除)が反映されないケースがあった。この手のイベントタイミング依存の問題を確実に解消するのは難しいため、`playerLeave`側は「できれば即座に」というbest-effortの位置づけにとどめ、代わりに**`startWrenchHighlightLoop`の定期ループ(`reconcileAllRangeIndicators`)で全ネットワーク分のインジケータを毎回再計算する**方式にした。`isAnyoneEditingNetwork`はオンライン中のプレイヤーしか見ないため、ログアウトした時点でそのプレイヤーの分は(`wh:editing_network`を消し忘れていても)自動的に「編集中ではない」扱いになり、次の周期(`HIGHLIGHT_INTERVAL`=10tick=0.5秒)以内に確実に壁が消える。個々のイベント処理の成否に依存せず「今の状態を見て合わせる」定期実行に寄せることで解消した。
- **(実機で発見された不具合の修正済み) スポーン直後に壁が「移動する」ように見える**: 側面4枚は当初、`dimension.spawnEntity()`でスポーンした直後に`entity.setRotation()`で回転させていたが、回転が反映されるまでの1〜2フレームはYaw0(未回転)の位置で描画されてしまい、そこから正しい位置へ一瞬で移動するように見えていた。`SpawnEntityOptions.initialRotation`でスポーンと同時に回転を指定する形に変更し、常に最初から正しい向きで描画されるようにした。

### Drainモード: ストレージを預け入れ対象外にする

倉庫レンチをDrainモードにした状態でストレージを**Shift+右クリック**すると、そのストレージの「Drain指定」がトグルされる。

- **効果**: Drain指定されたストレージは、①預け入れ・自動預け入れの預け入れ先として選ばれなくなり、②倉庫の整理では逆に中身を他の(Drain指定でない)ストレージへできる限り退避させる対象になる(退避先がどこにも無ければ残る)。引き出しには影響しない。
- **永続化**: `network.storages`(構造情報)は変更せず、ターミナル設定と全く同じ発想で、ストレージの座標に紐づく非表示エンティティ(`wh:storage_settings`)の動的プロパティ(`wh:drain`)に持たせる(`storageSettings.ts`)。理由もターミナル設定と同じで、今後ストレージ側の設定項目が増えても`network.storages`のJSON構造自体は変えずに済むため。
- **二連チェストの扱い**: 二重登録防止の都合上、二連チェストは物理的に2ブロックあっても`network.storages`には片方しか登録されない。Drain指定はプレイヤーがどちらの物理ブロックをクリックしても同じ効果になってほしいため、`resolveStorageMembership`で「クリックした場所が未登録でも、中身を共有する登録済みの隣を探して所属ネットワークを解決する」処理を行い、実際の設定は登録済みの座標に対して行った上で、`findPhysicalStoragePair`で見つかるもう片方の物理座標にも同じ値を書き込む(常に両方が同じDrain状態を持つ)。
- **預け入れ・整理側の絞り込みは「ネットワークにつき1tick1回」**: Drain判定(`getDrain`)は非表示エンティティの検索を伴うため、`insertIntoStorages`の呼び出しごと(=ラインごと)に毎回問い合わせるとコストが積み重なる。既存の`buildStorageIndex`(預け入れの優先スタッキング索引)と同じ考え方で、`processNetworkDeposits`/`processNetworkOrganize`がネットワークごとに1tick1回だけDrain指定ストレージの一覧を作り、`insertIntoStorages`に絞り込み済みの候補先リストとして渡す。
- **倉庫の整理でのDrain退避**: `compactKeyInStorages`を2段階にした。フェーズ1でDrain指定ストレージそれぞれの中身を`insertIntoStorages`(候補先を非Drainストレージに絞ったもの)で退避し、フェーズ2で残った非Drainストレージ同士を従来通り圧縮する。フェーズ1はデータの流れとしては「Drain指定ストレージを預け入れ元、他のストレージを預け入れ先」とする預け入れ処理そのものなので、既存の`insertIntoStorages`をそのまま再利用できた。
  - **(実機で発見された不具合の修正済み)** 退避先(非Drainストレージ)がその時点で満杯だと退避が0件で終わるケースがあるが、修正前は`compactKeyInStorages`がこれを「(予算切れではなく)処理完了」として扱い、そのラインを即座に`done`確定させていた。`submitOrganize`はネットワーク全品目を一度に1件ずつのラインとしてキューに積むため、`processNetworkOrganize`のループはある1品目のラインを処理した直後に別の品目のラインへ進むことがある。後続の品目のフェーズ2圧縮(部分スタックの統合)によって非Drainストレージに新しい空きスロットが生まれても、既に`done`確定させてしまった品目は二度と退避を試みないため、退避先の一部がまだ埋まりきっていないにもかかわらずDrainストレージにアイテムが残ったまま整理全体が完了扱いになってしまっていた(実機で、Drain指定ストレージにスタック可能なアイテムが残っているのに整理が終了する不具合として報告された)。
  - 修正: `compactKeyInStorages`の戻り値に`budgetExhausted`(予算切れで中断したか)を追加し、「予算切れ」と「退避先が(その時点で)満杯で1個も退避できなかった」を区別できるようにした。後者の場合はラインを`done`にせず、その代わり`processNetworkOrganize`内のtickローカルな`Set`(`stuckThisTick`)に加えて今回のtickでは後回しにする(同じラインを選び直す無限ループを防ぐため)。`stuckThisTick`はtickごとに新規に作るので、次tickでは必ず再挑戦する。これにより、他の品目の圧縮で空きスロットが生まれた後に、行き詰まっていた品目の退避が自然に再開されるようになった。
  - **(実機での要望を受けた追加修正)** 上記の修正だけだと、退避先に二度と空きが生まれようが無い場合にまで無限に再試行し続けてしまい、「Drain対象のストレージが空にならない限り整理が終わらない」状態になっていた。当初は「退避先(非Drainストレージ)全体が、空きスロットも積み増せるスタックも無いという意味で完全に満杯かどうか」をtickに1回判定し、真なら諦めるという実装(`isRegularStorageCompletelyFull`)を試みたが、これは不十分だと判明した: 例えば非Drainストレージが「丸石64個(満杯)」「鉄50個(端数、14個分の空きあり)」の2枠で、Drain側に丸石20個が残っているケースを考えると、鉄のスタックに空きがあるというだけで「まだ完全には満杯ではない」と判定されてしまうが、その空きは鉄でしか埋まりようがなく丸石には永久に使えないため、結局同じ無限リトライ不具合が別の形で再発する。「ストレージ全体に何らかの空きがあるか」という粗い判定では、その空きが今行き詰まっている品目にとって実際に意味があるかを区別できないことが原因。
  - 正しい修正: `isRegularStorageCompletelyFull`は削除し、代わりに「そのtickで残っている未完了ラインを一通り試して(行き詰まったラインは`stuckThisTick`に積んで後回しにしつつ)、1個も動かせなかった(`movedThisSweep === 0`)」ことをもって初めて「本当にもう手段が尽きた」と判断するようにした。この場合、その時点で`stuckThisTick`に残っている全ラインを`done`にして諦める。1個でも動いた品目があれば(=退避先の状態が変化した可能性がある)、`stuckThisTick`のラインは`done`にせず、次tickで(丸ごとリセットされる`stuckThisTick`により)再挑戦させる。この方式は品目ごとの空き状況を直接的な「進捗があったかどうか」で判定するため、鉄のような「動かしようのない端数」に惑わされず、丸石が本当に手詰まりであることを正しく検出できる。
- **Drain指定ストレージのハイライト**: 編集セッション中のプレイヤーに対し、構築モードの強調表示(`minecraft:villager_happy`、接続済み全メンバー)とは別に、Drainモードでは編集中のネットワークの**コントローラ+接続済み全ストレージ**を対象に、Drain指定済みのストレージは`minecraft:villager_angry`、それ以外(コントローラ、未指定のストレージ)は`minecraft:villager_happy`で示す(`highlightEditingNetwork`がモードで分岐)。Drain指定済みのものだけを表示する案も検討したが、「どれがそもそもDrain指定の対象になるのか(=接続済みなのか)分からない」「コントローラの位置も常に見えてほしい」という指摘を受け、構築モードと同じ範囲(コントローラ含む全接続済みストレージ)をベースに、Drain指定の有無だけを色で区別する形にした。

**(実機で発見された重大な不具合の修正済み)** Drain指定した(=設定エンティティが実在する)ストレージを破壊すると、条件によっては**その跡地に二度とブロックを設置できなくなる**不具合があった。原因は`storageLifecycle.ts`の破壊監視(`registerStorageBreakWatcher`)が、設定エンティティの削除(`removeSettingsEntity`)を`findMembership`が「登録済みストレージだ」と判定できた場合**のみ**行っていたこと。これが失敗する(=エンティティが削除されずに残る)ケースが2つあった。

1. コントローラを先に破壊してネットワークデータごと解体した後、登録済みストレージを破壊した場合 → `findMembership`がネットワーク自体を見つけられず、判定が失敗する。
2. 二連チェストの「登録されていない方の半分」(Drain指定は反映されているが`network.storages`には載っていない側。3章参照)を破壊した場合 → `findMembership`はそもそもこのブロックをストレージとして認識できないため、判定は常に失敗する。

残った設定エンティティ(`minecraft:collision_box`を持つ)が、その後ずっとブロックの再設置を妨げていたと考えられる。修正: 設定エンティティの削除は`findMembership`の成否に関係なく、破壊されたブロックの座標に対して**常に**試みるようにした(`removeSettingsEntity`は対象が無ければ何もしない安全な操作なので、常に呼んでよい)。ネットワークデータの削除(`removeStorage`)は引き続き`findMembership`の判定結果に従う(ネットワークが既に無ければ元々何もしない)。

なお、この修正は今後の再発を防ぐものであり、**この不具合が発生した時点で既に置けなくなっている場所は、コード修正だけでは直らない**(残留エンティティ自体を個別に削除する必要がある。例:`/kill @e[type=wh:storage_settings,x=<X>,y=<Y>,z=<Z>,r=1]`のようなコマンドで対象座標に絞って削除する)。

### 二連チェストの二重登録防止（実装・実機で発見された不具合の修正済み）

バニラの二連チェストは隣接する2つの独立したブロックだが、中身(コンテナ)は実質1つを共有している。両方を別々にストレージとして登録すると、カタログスキャンや抽出処理で同じ中身を二重にカウントしてしまう。これを接続時に検知して防止する。

判定方法は何段階か失敗を経て以下に落ち着いた。

1. **(誤り)隣接する同種ブロックの有無で判定** → 連結していない単体チェスト同士が偶然隣接しているだけでも誤検知した。
2. **(誤り)コンテナのスロット数(27超か)で判定** → `[A1 A2 B1 B2]`のように、別々の二連チェストが隣接して並んでいる場合、A2とB1はどちらも54スロットで隣接しているが実際には中身を共有していない、という偽陽性を防げなかった。
3. **(採用)実際に中身を共有しているかを直接確認する**: 対象コンテナのスロット0の中身を退避し、一意な`nameTag`を持つ目印アイテムを一時的に置いて、隣接コンテナ側から同じ目印が見えるか確認し、確認後は必ず元の中身に戻す。同期的に完結するため見た目には一切影響しない。

検討した代替案（ブロック状態から直接読み取る、コンテナオブジェクトの参照同一性`===`を使う）はどちらも採用しなかった。前者はBedrockのチェストに連結情報を持つブロック状態が存在しない（Java版の`type: left/right/single`に相当するものがない）ため不可能。後者は挙動が非公開でドキュメントに保証がなく、他の未検証の思い込みで既に2回つまずいた反省から避けた。

この判定は「レンチで未接続のコンテナを接続しようとした瞬間」にのみ呼ばれる。定期実行のループ（強調表示・コントローラのtick処理）では一切呼ばれない。

```ts
function containersShareStorage(a: Container, b: Container): boolean {
  if (a.size !== b.size || a.size === 0) return false;
  const probeSlot = 0;
  const original = a.getItem(probeSlot);

  const marker = new ItemStack("minecraft:stick", 1);
  marker.nameTag = `wh:probe:${Date.now()}:${Math.random()}`;
  a.setItem(probeSlot, marker);

  let shared = false;
  for (let i = 0; i < b.size; i++) {
    if (b.getItem(i)?.nameTag === marker.nameTag) { shared = true; break; }
  }
  a.setItem(probeSlot, original); // 必ず元に戻す
  return shared;
}
```

### ターミナルは同時に1つのネットワークにしか接続できない（実機で発見された不具合の修正済み）

ストレージは複数のネットワークに重複接続されていても実害が無い（単に両方のネットワークから在庫として見える・両方の整理/預け入れ対象になるだけ）ため許容しているが、**ターミナルは違う**。ターミナルは`submitOrder`/`submitDeposit`で「どのネットワーク宛か」を1つに決めて引き出し/預け入れを送信する一方、自動端末の定期チェックやレンチのハイライトは`network.terminals`を各ネットワークごとに独立して走査するため、同じ物理的なターミナルが複数のネットワークの`terminals`に同時に登録されると、どちらのネットワーク相手として処理すべきかが曖昧になり誤動作した(実機で確認済み)。

修正: レンチでターミナルを接続しようとした時、そのターミナルが**既に別のネットワークに接続済み**であれば(`findMembership`で判定)、新規接続を拒否してメッセージを表示する。ストレージの二重登録防止(`findAdjacentConnectedStorage`)とは別の問題（こちらは物理的に同じ収納を二重カウントする話、ターミナルの方は同じ1台が2つの論理ネットワークに属することの曖昧さの話）だが、どちらも「レンチで接続しようとした瞬間にチェックする」という対処のタイミングは共通。

この修正より前に誤って複数ネットワークに接続してしまったターミナルは、コードの修正だけでは直らない。該当ネットワークをそれぞれ編集モードで開き、不要な方からレンチで切断(Shift+右クリック)して、最終的に1つのネットワークだけに接続された状態に手動で戻す必要がある。

## 4. コントローラのtick処理

`system.runInterval`によるグローバルなポーリングで実装する。ブロック自体はティックを持たず、受動的なデータ構造として存在する。MVP当初は固定20tick間隔の単一ループだったが、後にコントローラの「周期」アップグレード軸によりネットワークごとに実際の間隔が変わるようになった(詳細は本章「グレード管理」参照)。

### スループット制（グレード拡張性のため）

「引き出しを一括即時処理」ではなく、**コントローラのグレードに応じた搬送予算(budget)** を消費しながらキューを進める設計にする。これにより、将来「グレードの高いコントローラほど速い」という演出が、フェイクの待ち時間ではなく実際のスループットとして自然に実現できる。MVPでは`throughputPerTick`を十分大きい固定値にすることで、実質的に即時処理と変わらない挙動になる。

**用語の注意（実機での指摘を受けて整理）**: `ORDER_THROUGHPUT_PER_CYCLE`/`DEPOSIT_THROUGHPUT_PER_CYCLE`/`ORGANIZE_THROUGHPUT_PER_CYCLE`という名前が示す通り、この予算は**Minecraftのサーバーtick単位のレートではなく、コントローラの処理ループが1回実行されるたびの予算**である。処理ループ自体は`networkProcessing.ts`の`NETWORK_PROCESSING_INTERVAL_TICKS`(=20)により、サーバーtick20回につき1回だけ実行される。当初は`*_PER_TICK`という名前で、コントローラUIの「状況」タブにもそのまま「/tick」として表示していたが、これは実際のサーバーtickの20倍速く見えてしまう誤解を招く表示だった。修正: 定数名を`*_PER_CYCLE`に変更して意味を明確にした。UI表示側は、値をサーバーtickあたりのレートに割り算して換算する案も検討したが、割り算した数値だけを見せても結局「これは何のtick単位なのか」が伝わらないという指摘を受け、`controllerUi.ts`の`throughputLabel()`で**「値/サイクルのtick数」**（例:「10/20tick」）とサーバーtick数の分母をそのまま併記する表示にした。

```
runInterval(20 ticks) {
  for (network of allNetworks) {
    moveReadyIssuingEntriesIntoQueue(network); // wh:issuing -> wh:orders

    let budget = getThroughput(network.controller.tier); // MVP: 十分大きい固定値

    while (budget > 0 && queue(network) not empty) {
      const order = queue(network).front();
      const line = order.lines.find(l => !l.exhausted && l.delivered < l.requested);

      if (!line) {
        finalizeOrder(order); // shortfallがあれば wh:partial:<id> に記録し、キューから除去
        continue;
      }

      const attempt = min(line.requested - line.delivered, budget);
      const extracted = extractFromStorages(network, line, attempt, terminalContainer);
      // extractFromStorages はストレージからの抜き取りとターミナルへの格納を
      // 同一関数内でアトミックに行う。「宙に浮いた」アイテムは発生しない。
      line.delivered += extracted;
      budget -= extracted;

      // extracted < attempt は「予算不足」ではなく「真の在庫 or 受け皿不足」を意味する
      // (attempt自体が budget で既に絞られているため)
      if (extracted < attempt) line.exhausted = true;

      persistQueue(network); // ← ラインを1つ処理するたびに書き戻す(後述)
      if (budget <= 0) break; // 続きは次tickへ持ち越し
    }
  }
}
```

**搬入先（ターミナルの張り付いた先のストレージ）が満杯で格納できない場合も、ストレージ側の在庫不足と同じ「不足」として扱う**（`exhausted = true`）。搬入先に有効なコンテナが無い場合（張り付いた先に何も無い、コンテナでない等）も同様に、全ラインを不足として`wh:partial`に記録した上で引き出しを打ち切る。

### 永続化の粒度: ラインごとに書き戻す

ウォッチドッグ（実行時間が長すぎるスクリプトを強制中断する仕組み）が処理途中で発火しても、「実際にアイテムが移動した分は必ず`delivered`にも反映済み」という不変条件を保つため、**ラインを1つ処理するたびに`world.setDynamicProperty`で書き戻す**。個人利用規模なら書き戻し回数が増えてもパフォーマンス上の問題にはならない。

これにより、ゲームを閉じる/クラッシュするタイミングがどこであっても、再読み込み後は`wh:orders:<networkId>`に残っている引き出しがそのまま「続きから」処理再開される。特別な復旧処理は不要。ターミナル・ストレージのコンテナ内容自体は、通常のチェストと同じくMinecraft標準のブロック永続化に乗っかるだけでよい。

### 「ターミナルが消えた」判定はネットワーク登録データを正とする（実機で発見された不具合の修正済み）

`THROUGHPUT_PER_TICK`を小さくして複数tickにまたがる処理を実機で試したところ、処理途中でワールドを出て入り直すと、引き出しがプレイヤーに見える形では消えてしまう不具合があった。原因は、引き出しラインの処理時に「ターミナルの位置に今`dimension.getBlock()`でブロックを取得できるか」だけを見て、失敗したら即座に「ターミナルが破壊された」とみなして引き出しを打ち切っていたこと。ワールド再読み込み直後は、プレイヤーの現在地に近いチャンクから先に読み込まれるため、ターミナルのあるチャンクがまだ読み込まれていないタイミングでtickが走ると、ブロックがまだ取得できず誤判定していた（`wh:partial`には記録されるが、ターミナル側はそれを読み出さないため、プレイヤーからは「消えた」ように見える）。

修正: 「ブロックが今取得できるか」ではなく、**`network.terminals`(ネットワークへの登録データ)を正とする**。

- `order.terminal`(または`request.terminal`)が`network.terminals`に含まれていなければ、本当に切断/破壊されたとみなして打ち切る(このリストの更新は`wh:terminal`ブロックの`onPlayerBreak`かレンチによる明示的な切断でしか起きないため、信頼できる)。
- 含まれているのに`dimension.getBlock()`で取得できない/型が違う場合は、チャンク未読み込み等の一時的な状態の可能性が高いため、**打ち切らずにそのtickの処理を諦めて次tickに再試行する**(FIFOを守るため、後続の引き出しの処理には進まずbreakする)。

### ターミナルの発行遅延（グレード拡張性のため）

「確定」を押した瞬間に本キューへ積むのではなく、いったん`wh:issuing:<networkId>`に積み、ターミナルのグレードに応じた遅延(`getIssueDelay(tier)`、MVPでは0)の後に本キューへ移す。`system.runTimeout`ではなく上記の同じポーリングループに乗せることで、ワールド再読み込みをまたいでも状態が失われない。

### 引き出し・預け入れ・整理のキャンセル(専用の優先キュー)

コントローラUIの「状況」タブ(`controllerUi.ts`)から、進行中の引き出し・預け入れ・整理をキャンセルできる。**巻き戻しは行わない**: 既に配送/格納/整理済みの分はそのまま処理済みの状態を維持し、まだ処理していない残りだけが無かったことになる(過去に遡って在庫を戻す処理は複雑さの割に得るものが少ないと判断し、MVPでは対象外とした)。引き出し側(`orderProcessing.ts`)・預け入れ側(`depositProcessing.ts`)・整理側(`organizeProcessing.ts`)は全く同じ設計をそれぞれ独立に実装している。

- **厳密なIDが必要**: 通知等の表示に使っている`Order.id`(`generateOrderId()`、英数字4桁)は「マルチプレイでチャット上に表示された時に見分けられればよい」という表示用途のための緩いIDで、厳密な一意性を保証しない(4章冒頭、5章参照)。誤って別の引き出しを取り消してしまわないよう、キャンセルには`Order.requestId`という別の一意ID(`generateId()`、他のリクエストIDと同じ仕組み)を新設し、こちらだけをキャンセル指定に使う。**預け入れ・整理は元々`DepositRequest.id`/`OrganizeRequest.id`自体が`generateId()`による厳密な一意ID**(表示用の緩いIDを持たない設計だった)なので、`requestId`を新設する必要は無く、`id`をそのままキャンセル指定に使える。後から表示用ID(`displayId`)をそれぞれ追加した際も、この`id`(厳密)/`displayId`(表示用)の役割分担は変えていない。
- **専用の優先キュー**: キャンセル要求は通常の`wh:orders`/`wh:issuing`とは別の`wh:order_cancels:<networkId>`(`requestId`の配列)に積むだけの軽量な操作(`cancelOrder`)。`processNetworkOrders`は毎tickの先頭で(`moveReadyIssuingEntries`より前に)このキューを消費し、`wh:issuing`・`wh:orders`の両方から該当`requestId`を除去してから、通常の引き出し処理に進む。「専用キュー+毎tick先頭で優先処理」という構成により、次にその引き出しが処理される前に確実に取り除ける(通常のFIFOに割り込ませて優先度を上げる、というような複雑な仕組みは不要)。預け入れ側も`wh:deposit_cancels:<networkId>`/`cancelDeposit`/`processDepositCancels`として、整理側も`wh:organize_cancels:<networkId>`/`cancelOrganize`/`processOrganizeCancels`として全く同じ構成で実装した(整理は発行待ち(issuing)相当のステージングキューが無く`wh:organize`一本なので、そこだけ除去すればよい分、実装はやや単純)。
- **UI側の即時反映**: 実際の除去は次tickまで反映されないため、コントローラUIの「状況」タブでは、キャンセルした`requestId`をUIセッション内の`Set`で覚えておき、一覧の再取得時にそこから除外することで、体感的には即座に一覧から消えるようにしている(引き出し・預け入れ・整理のセクションそれぞれが独立した`Set`を持つ)。

### グレード管理: 複数軸に対応したアップグレード機構

実際に使ってみると、機能ごとに1グレードのアイテムしか無いのは窮屈だという要望を受け、以前の構想(整数ブロックステート`wh:tier`によるグレード管理)を、**1つのブロックが複数の独立した強化系統を同時に持てる**形に一般化して実装した。

**汎用の「アップグレード軸」抽象**(`upgrade.ts`)を用意し、ブロック種別に依存しない共通の型・関数にした。

```ts
type UpgradeAxis = {
  id: string;            // 内部識別子(例: "controller_speed")
  label: string;         // UI/メッセージ表示用の名前(例: "速度")
  blockTypeId: string;   // このアップグレードが有効なブロックのtypeId
  stateKey: string;      // このブロックが持つカスタムブロックステート名(例: "wh:speed_tier")
  kitItemIds: string[];  // index i の要素 = Tier i -> i+1 に使うキットのアイテムtypeId
};
```

- **Tierはネットワークデータではなくブロック自体に持たせる**: 「ターミナルごとのローカル設定」(6章)と同じ発想で、所属情報(`network.controller`等の座標)と個々の状態を分離している。
- **壊さずにその場でTierを上げる**: コントローラを破壊すると`destroyNetwork`でネットワークごと解体される(2章)ため、アップグレード操作は`block.setPermutation()`でブロックステートだけを書き換える(破壊イベントは発生しない)。専用の消費アイテム(アップグレードキット)を対象ブロックに`onUseOn`で直接使う方式にした。レンチのモード切替とは別にした理由は、レンチが「何度でも使える設定ツール」という設計思想を持つのに対し、アップグレードは本来消費される性質の操作で噛み合わないため。
- **実装上の注意**: `BlockPermutation.getState`/`withState`の型は`minecraftvanilladata.BlockStateSuperset`(バニラの既知ステートのみ)を対象にしたジェネリックで、`"wh:speed_tier"`のようなカスタムステート名は型に存在しない。読み取りは`getAllStates()`(型が緩く安全)を使い、書き込みは`withState`の引数を`as any`でキャストしている。このアドオンでカスタムブロックステートを使うのはこれが最初のため、この制約がここで初めて表面化した。

**現在実装済みの軸はコントローラの「速度」「周期」「範囲」の3つ**(`controllerAxes.ts`の`CONTROLLER_SPEED_AXIS`/`CONTROLLER_CYCLE_AXIS`/`CONTROLLER_RANGE_AXIS`)。発行遅延・自動チェック間隔は今回も対象外(将来、同じ枠組みで別の軸として追加する想定)。

**速度軸**: 引き出し/預け入れ/整理のスループット(旧`ORDER_THROUGHPUT_PER_CYCLE`等の固定定数)を、各処理モジュール(`orderProcessing.ts`/`depositProcessing.ts`/`organizeProcessing.ts`)がTier0〜4の5段階のテーブル(`getOrderThroughput(tier)`等)として持つように変更し、`processNetworkOrders`等が毎サイクル`getAxisTier(dimension, network.controller, CONTROLLER_SPEED_AXIS)`で実際のTierを読んで予算を決める。搬入出(引き出し`ORDER_THROUGHPUT_BY_TIER`/預け入れ`DEPOSIT_THROUGHPUT_BY_TIER`)は`[128, 192, 384, 1024, 4096]`で共通。整理(`ORGANIZE_THROUGHPUT_BY_TIER`)はネットワーク外部とやり取りしない内部処理という性質上、搬入出のちょうど4倍`[512, 768, 1536, 4096, 16384]`にしている。

**周期軸**: サイクル(引き出し/預け入れ/整理をまとめて1回処理する単位)自体の間隔(tick数)を変える軸。`networkProcessing.ts`の`CYCLE_TICKS_BY_TIER = [100, 80, 50, 25, 10]`(値が小さいほど頻繁に回る=速い)。MVPでは`system.runInterval`を固定20tickの単一間隔で回し、全ネットワークを毎回まとめて処理していたが、ネットワークごとに間隔を変えるには単一の`runInterval`では表現できない(間隔はコールバック登録時に固定されるため)。そこで、**基準ループを`BASE_LOOP_INTERVAL_TICKS`(=5、最短のTier4=10tickより十分細かい)で回し、ネットワークごとに「前回処理からの経過tick」を`Map<networkId, lastProcessedTick>`(メモリ上のみ、永続化しない)で管理し、`system.currentTick - last >= cycleTicks`になった時だけそのネットワークを処理する**方式にした。`currentTick % cycleTicks === 0`のような剰余判定も検討したが、基準ループの間隔とTierごとの間隔の両方が互いに割り切れる関係である前提に暗黙に依存してしまい、将来どちらかの値を変えた時に静かに周期がずれる恐れがあったため、経過tickの直接比較にした(基準ループの間隔より短い誤差は生じるが、無視できる程度)。`lastProcessedTick`はワールド再読み込みで消えても、次の基準ループですぐ再計測されるだけで実害が無い。コントローラUIには`getCycleIntervalTicks(tier)`から実際の値を計算した表示があり(アップグレードタブの周期軸の行。後述)、以前固定`NETWORK_PROCESSING_INTERVAL_TICKS`定数を表示していた箇所を置き換えている。

**範囲軸**: コントローラの接続可能範囲(3章「ネットワークの接続範囲」の`getRangeForTier(tier)`、`[3, 4, 6, 9, 16]`)を変える軸。速度軸・周期軸とは異なり、この軸だけ**Tier変更に伴う副作用**(接続範囲が縮んだ結果、既存の接続先が範囲外になった場合の自動切断)を必要とするため、`UpgradeAxis`型に任意の`onTierChanged?: (dimension, block, player?) => void`フックを追加した(範囲軸以外は`undefined`のままで既存コードは無変更)。呼び出し元は`upgradeKit.ts`の`onUseOn`(`setAxisTier`直後)と`controllerUi.ts`の「取り出す」ボタン(`setAxisTier(block, axis, 0)`直後)の2箇所。範囲軸の`onTierChanged`(`controllerAxes.ts`の`pruneRangeAxisMembers`)は、新しいTierの範囲で`network.ts`の`pruneOutOfRangeMembers`を呼び、範囲外になったストレージ/ターミナルを`removeStorage`/`removeTerminal`で切断する。**これは3章で明記した「切断は範囲外でも常に許可する(遡って強制切断はしない)」という一般方針に対する、範囲軸のTierダウン時に限定した意図的な例外**である(ユーザーからの明示的な要求)。Tierが上がる場合もこの処理を素通りさせている(範囲外に出るメンバーは存在せず無害なため、増減を区別する分岐をあえて設けていない)。切断したストレージについては手動切断(`wrench.ts`)と同じく設定エンティティ(`storageSettings.ts`)も掃除するが、ターミナルは手動切断でも掃除していない既存の非対称性に揃えて何もしない。`network.ts`自体はアップグレード軸の仕組みを知らない(循環import回避のため引数で範囲を受け取るだけ)。可視化の詳細(Tierごとのサイズ変更)は3章参照。

**アップグレードキット**: 軸ごと・Tierごとに別アイテムにした(Tier1〜4の4段階。クラフトレシピを実在の鉱石格上げ順に無理に合わせる必要がないよう、汎用的な`Tier N`命名にしている。速度軸は`wh:speed_kit_tier1`〜`wh:speed_kit_tier4`、周期軸は`wh:cycle_kit_tier1`〜`wh:cycle_kit_tier4`、どちらも汎用コンポーネント`wh:upgrade_kit`を共有)。目標Tierに到達するための専用アイテムなので、ブロックが今何Tierかが一目で伝わる。表示名は`T{n} 速度強化キット`のようにTier番号を先頭に付ける形式にしている(`速度強化キット(Tier n)`という後置形式から変更)。既存の`ATM-`/`INV-`/`端末-XXXX`(6章・7章)と同じ「短い接頭辞で種別を一目で示す」慣習に揃えたほか、先頭がTierになることでインベントリ内で同じTierのキットが軸を跨いで近くに並ぶ副次的な利点もある。

キットは**どのTierのものでも直接使え(飛び級可)、使うとそのキットのTierに一気に設定される**。軸ごとに同時に装着できるキットは1つだけだが、既に何か装着済みの状態で別のキットを使った場合は「取り外してから装着し直す」のではなく、**その場で置き換わる**(元のキットは`giveOrDropKits`でプレイヤーへ返す。インベントリ優先・満杯なら足元へドロップという、破壊時・UIの「取り出す」ボタンと同じ返却挙動に統一している)。同じTierのキットを使おうとした場合は何もしない(メッセージのみ)。使用すると`setPermutation`でTierを直接書き換え、手持ちのスタックを1個消費する(`upgradeKit.ts`)。

当初は「現在のTierがちょうどそのキットの`fromTier`と一致する場合にのみ使え、1段ずつしか上げられない」という順送り方式だったが、レシピ側で上位キットが下位キットを消費する構成(後述)にすると、ブロックへ直接使う分とレシピ消費用の分とで下位キットを二重に用意する必要が生じてしまうことに気づき、飛び級可の方式に変更した。この変更により、プレイヤーは目的のTierのキットをレシピの階段を上って1個作るだけでよく、道中のTierをブロックにも別途装着する必要がなくなった。

判定・消費対象アイテムのテーブルは、各ブロックが持つ`UpgradeAxis`の配列から`kitItemIds`を辿って自動的に導出しているため、軸(あるいは別のブロック種)が増えても`upgradeKit.ts`自体は変更不要で、参照するaxes配列を合成するだけでよい(実際、周期軸の追加時もこのファイルは無変更だった)。周期キットは速度キットと同じ素材色だが、アイコンの形をリング状にして軸違いを判別できるようにしてある(`tools/generate-placeholder-icon.mjs`の`upgradeKitRingColorAt`)。範囲キットは同様に四角い枠(額縁、「囲む範囲」の比喩)の形にしている(`upgradeKitSquareColorAt`)。

**循環import回避のための`controllerAxes.ts`分離**: `CONTROLLER_SPEED_AXIS`は当初`controllerBlock.ts`に直接定義していたが、`controllerBlock.ts`は`showControllerUi`のために`controllerUi.ts`に依存し、`controllerUi.ts`は表示のために`orderProcessing.ts`等の処理モジュールに依存している。そこへ処理モジュール側からスループット計算のために`controllerBlock.ts`のaxis定義をimportすると、`orderProcessing.ts → controllerBlock.ts → controllerUi.ts → orderProcessing.ts`という循環importになってしまう。そのため、軸の定義(`CONTROLLER_BLOCK_ID`/`CONTROLLER_SPEED_AXIS`/`CONTROLLER_AXES`)だけを、`upgrade.ts`にしか依存しない末端モジュール`controllerAxes.ts`に切り出した。

**破壊時の挙動**: 対象ブロックを破壊すると、design.mdの既存方針(2章、破壊するとネットワークごと解体される)と一貫させ、Tierは0にリセットされる。ただし素材を無駄にしないため、`onPlayerBreak`で`event.brokenBlockPermutation`から破壊直前の軸ごとのTierを読み取り、それまでに消費したキットを軸ごとに返してから(`giveOrDropKits`、ネットワークの有無に関わらず必ず行う)、既存のネットワーク解体処理を行う。失われるのは「積み上げたTierという状態」だけで、素材そのものは失われない。

**UI表示**: コントローラUIに専用の「アップグレード」タブを追加した(「状況」「整理」「アップグレード」「設定」の4タブ構成)。`CONTROLLER_AXES`をループするだけの実装なので、軸が増えても自動的に「Tier表示+効果の内訳+取り出すボタン」の組が1つ増える。各軸につき、現在Tierを`{軸名} Tier {n} / {最大Tier}`の形式で表示するラベル、その軸の実際の効果の内訳(速度軸なら「引き出し／預け入れ／内部」の3行、周期軸なら「周期」の1行)、「取り出す」ボタンを表示する。**スループット/周期の表示は当初「状況」タブに独立して置いていたが、アップグレードの効果を確認する場所として一本化した方が分かりやすいという要望を受け、各軸のTier表示の直下に移動した**(「状況」タブは引き出し/預け入れ/整理の進行中リストのみになった)。表示単位も、以前は`throughputLabel()`で「値/サイクルのtick数」(例:「128/20tick」、分母は当時グローバル固定だった`NETWORK_PROCESSING_INTERVAL_TICKS`)としていたが、周期が軸ごと・Tierごとに変わるようになったため、速度側の内訳は分母を持たず`{値}/cycle`という単位だけの表示にし(`perCycleLabel()`)、実際のtick数は周期軸自身の`{tick数}tick/cycle`という行(`cycleIntervalLabel()`)で独立して示す形にした。こうすることで、速度軸の内訳表示が周期軸のTierに依存しなくなり(=別の軸の状態を跨いで参照しない)、片方の軸だけ取り出した時に**もう一方の表示が古いままになる不整合が構造的に起きない**。Tierラベル・内訳ラベルはいずれも`ObservableString`にしてあり(DDUIの`CustomForm`は素の文字列を渡すと開いた時点の値のまま固定されてしまうため)、取り出すボタンを押した瞬間に`setData()`で更新し、表示がその場で切り替わるようにしている。ボタンの`disabled`にも同様に`ObservableBoolean`(Tier0かどうか)を渡し、アップグレードが1段も入っていない間は非活性になる(取り出した直後もtrueに戻す)。ブロックの見た目(Tierごとのテクスチャ切り替え)は今回のスコープに含めていない(8章の既存方針「グラフィックの作り込みは後回し」を踏襲。プレイヤーへのフィードバックはUI上のTier表示で最低限確保している)。

**アップグレードの取り出し**(`giveOrDropKits`、`upgrade.ts`): ブロックを破壊しなくても、UIのボタン1つで装着済みのキットを取り外せるようにした。破壊時のドロップと同じ関数を再利用し、`setAxisTier(block, axis, 0)`でTierを0に戻す(`setPermutation`によるその場書き換えなので、こちらもブロックの破壊やネットワークの解体は伴わない)。**返し方はブロックの隣への単純ドロップではなく、プレイヤーが分かる場合はまずインベントリへ直接渡し、入りきらなかった分だけをプレイヤーの足元にドロップする**(`Container.addItem`の戻り値=入りきらなかった分をそのまま`dimension.spawnItem`する)。UIのボタンは常にプレイヤーが分かるのでインベントリ優先になり、ブロック破壊時も`event.player`が分かればインベントリ優先、分からない場合(まれ)のみ従来通りブロック位置にドロップする。

**実機で発見された不具合(修正済み): 手持ちアイテム操作APIの混在**。キットの置き換え(既に装着済みの軸に別のキットを使う、前述)を実装した際、「インベントリが満杯の状態でキットを使う→返却されたはずのキットが見当たらないが、ホットバーの1枠が中身不明のまま操作不能になり、Shift+クリック等で触れるとようやく中身が現れる」という不具合が実機で見つかった。当初はイベント処理中の同tick内でのインベントリ操作を疑い`system.runTimeout`で1tick遅らせたり、ドロップ位置をプレイヤーの足元からブロック付近に変えたりしたが改善せず、バニラアイテムの拾い直しや素手でのQ落下→拾い直しでは再現しないことから絞り込んだ結果、**`giveOrDropKits`が使う`player.getComponent("inventory")`のコンテナAPIと、手持ちの消費に使っていた`player.getComponent("equippable")`(`EquipmentSlot.Mainhand`)という、同じ手持ちスロットを指す2つの異なるコンポーネントAPIを同じ処理内で混在させていたこと**が原因だった。手持ちの消費側も`inventory`コンテナ経由(`player.selectedSlotIndex`)に統一したところ解消した(`upgradeKit.ts`の`consumeOneFromMainHand`)。1tick遅延やドロップ位置変更は原因ではなかったため元に戻している。

**新しい軸を追加する時にやること**(`upgrade.ts`自体は変更不要。範囲軸の追加で実際にこの手順通りだったことを確認済み):
1. 対象ブロックのJSONに新しいカスタムブロックステートを追加する(例: `"wh:range_tier": [0,1,2,3,4]`)。
2. そのブロックの軸定義モジュール(例: `controllerAxes.ts`)に`UpgradeAxis`をもう1つ追加し、対応する`*_AXES`配列に加える。Tier変更時に副作用が必要な軸だけ`onTierChanged`も指定する。
3. 新しいキットアイテム(BP item json + アイコン + lang)を用意する。
4. その軸のTierを実際の効果(例: `getRangeForTier`)に反映する箇所を1箇所追加する。

### クラフトレシピ: アップグレードキット・コントローラ

8章で「コントローラ/ターミナル/レンチのクラフトレシピは無し(`/give`/クリエイティブのみ)」としていたMVP方針を、アップグレードキット8種とコントローラ本体については覆した。単に希少な素材を積むのではなく、**素材そのものにTierやブロックの実際の挙動と結びつく意味を持たせる**ことを狙った(`BP/recipes/*.json`、すべて`minecraft:recipe_shaped`、`crafting_table`タグ)。

**キットの「タイプ」と「進行シンボル」**: アップグレードキットは`C`/`S`の2つの「タイプ」に分類され、タイプごとに1本の「進行シンボル」(ゲームの進行度そのものを象徴する素材)の階段を共有する。速度軸・周期軸はどちらも`S`タイプで、進行シンボルはTier1〜4で`石炭ブロック→ダイヤモンド→ネザライトインゴット→ネザースター`(採掘→ネザー資源開発→ボス討伐、という難易度の階段)。範囲軸は`C`タイプ(進行シンボル`鉄→ダイヤモンド→ネザライトインゴット→ヘビーコア`)を初めて使う軸になった。**進行シンボルを軸ごとに別の終盤コンテンツに紐付ける案(当初検討: 速度=ネザー系、周期=Deep Dark系)は不採用にした**。軸が増えるたびに新しい終盤コンテンツを探すのは種切れするため、「タイプ」という中間の粒度で共有する方式に落ち着いた。これは`UpgradeAxis`が「軸ごとの差分は最小限、残りは共通の枠組み」という設計だったのと同じ発想をレシピにも適用したもの。

**Tierごとに固定された形**(`コア`=中央、`意味`=その軸固有の機能を象徴する素材、`進行`=タイプ共通の進行シンボル):

- **Tier1/Tier2**: 四隅=進行×4、左右=意味×2、中央=コア。
- **Tier3**: 上・左・右=意味×3、下=進行×1、四隅は空。四隅が埋まっている状態(T1/T2)から急に空くことで、Tierが上がるごとに「量より質」に切り替わる感覚を表現している。
- **Tier4**: 左右の列(6マス、四隅+左右中央)=**そのキットのTier1の意味シンボル**×6、上=そのTierの意味シンボル×1、下=進行×1、中央=コア。9マス全てが埋まる唯一のTierで、「Tier1の意味シンボルが完成形を額縁のように囲む」形になっている。要求により、**Tier4だけは意図的に重く**してあり(進行シンボルはネザースター、意味シンボルもエンチャント済みの金リンゴ/エコーシャードのような入手困難な素材)、全ネットワークに気軽に付けられるものではない前提にしている。

**コア**: Tier1は棒。Tier2以降は前Tierのキットそのもの(=キットは飛び級可だが、レシピ上は積み上げ式)。将来、途中のTierが存在しない軸(例: Tier2が無い)ができた場合は、存在する直近のTierまでTier1側へ遡ってコアに使う想定。Tier1自体が存在しない軸ができた場合は、コアを額縁で代用する想定(いずれも未実装、方針のみ)。

**確定した中身**:

| | 意味シンボル(Tier1〜4) |
|---|---|
| 速度軸 | 金インゴット → ピストン → ホッパー → エンチャント済みの金リンゴ |
| 周期軸 | レッドストーンダスト → 時計 → レッドストーンリピーター → エコーシャード |
| 範囲軸 | ガラス → 竹 → スカルクセンサー → コーラスフルーツ |

速度軸は「ピストン(力ずくの推進)→ホッパー(自動搬送)→エンチャント済みの金リンゴ(格上げの極致)」、周期軸は「時計(時間そのもの)→リピーター(タイミング制御)→エコーシャード(反響=周期の象徴)」という並びにしてある。範囲軸は「ガラス(見通せる=視界が届く範囲)→竹(まっすぐ・速く伸びる)→スカルクセンサー(離れた振動を検知する)→コーラスフルーツ(エンド次元でのテレポート=距離を超える)」という、いずれも「遠くまで届く/伝わる」ことを連想させる並びにしてある。意味シンボルは当初「軸ごとに固定1種類、Tierが上がるごとに個数だけ増やす」案(速度=動力レール固定等)だったが、Tierごとに別の意味シンボルに変える案の方が「Tierが上がるほど機能が高度化していく」物語性を表現できるため、そちらを採用した。

**コントローラ本体**(`BP/recipes/controller.json`): 四隅=鉄インゴット(キット群と共通の構造材)、上=レッドストーンリピーター、下=製図台、左右=チェスト、中央=レッドストーンブロック。リピーター(周期を刻む)は「一定間隔でネットワークを監視する」というコントローラの実際の挙動(本章「スループット制」のtickポーリングループ)の比喩。製図台は「ネットワーク全体の構成(どこに何が繋がっているか)を把握する」というコントローラの役割の比喩。チェストは倉庫という機能そのものの直接的な比喩で、中央のレッドストーンブロックが処理を駆動する動力源にあたる。**T1アップグレードキットの方がコントローラ本体より安いという逆転が生じている**が、これは意図的な判断: T1は「コントローラ入手時にまず試してみる」程度の軽い位置づけであり、実際の強化幅(スループット等)も他のTierより控えめにしてあるため、入手コストが低くても違和感がないと判断した。

**ターミナル系列(基本ターミナル/自動端末/在庫管理ターミナル)**: 自動端末・在庫管理ターミナルは、基本ターミナルそのものをレシピの中央に消費する積み上げ式にした(アップグレードキットと同じ発想。「基本ターミナルを改造して自動化する」という物語性も出る)。基本ターミナルは四隅=鉄インゴット(構造材、他レシピと共通)、上下左右=ガラス×3+ホッパー×1、中央=コンパレーター(信号を読み取る=ネットワークのデータを問い合わせる、という機能の比喩)。ホッパーは「実際にチェストとアイテムをやり取りする」機能を素材面でも裏付ける狙いで、下に配置した。自動端末・在庫管理ターミナルは共通の骨格(左右=レッドストーンリピーター、下=時計、中央=基本ターミナル)を持ち、上の1マスだけ(自動端末=ドロッパー/在庫管理ターミナル=エンダーアイ)で機能を差別化する形にした。リピーターと時計はどちらも「時間」を象徴する素材で、どちらも定期チェック(7章、100tick=5秒間隔のポーリング)で動く機器であることをレシピ自体が語っている。ドロッパーは「信号を受けて自動でアイテムを排出する」バニラ機構そのもの(自動端末の自動搬送)、エンダーアイは「遠く離れた場所を見通す」道具(在庫管理ターミナルがネットワーク全体を見渡す点)の比喩。全て作成数1固定(「基本ターミナルを素材にしてカスタマイズする」という位置づけ上、1クラフトで複数出るのは不自然なため)。

**レンチ**: 「毎回持ち歩く消耗品ではなく、最初に1個作れば十分な設定用ツール」という位置づけのため、他のどのレシピよりも軽くしてある(銅インゴット×2+棒×1、意味シンボルなし)。ネットワーク機器群(鉄ベース)とは異なり銅を使うことで、「ネットワークの一部ではなく、個人が持つ道具」という立ち位置の違いも素材で表現している。

### 預け入れ（格納）: 引き出しと対称な逆方向の処理

引き出し（ネットワークのストレージ → ターミナルの張り付いた先）と対称な、逆方向の処理を追加した。ターミナルの張り付いた先のコンテナに入っているアイテムを、ネットワーク内のストレージ群へ配って格納する。

- データモデル・処理モデルは`Order`/`OrderLine`と完全に対称（`DepositRequest`/`DepositLine`、`wh:deposits:<networkId>`、`wh:deposit_issuing:<networkId>`、`wh:deposit_partial:<networkId>`）。`DepositRequest`は当初、表示用ID・実行者情報を持っていなかった（完了通知の仕組みが無いため、そもそも表示する機会が無かった）が、後に追加したコントローラUIの「状況」タブ(4章参照)で引き出しと同様の表示をしたいという要望を受け、`Order`と同じ形（`displayId`は`generateDepositId()`による表示用ID、`playerName`は実行者。自動預け入れは空文字列で「自動」表示になる、`AUTO_ORDER_PLAYER_NAME`と同じ扱い）を追加した。厳密な一意ID(`id`、キャンセル指定用)とは別に`displayId`を持つ点は、`Order`(`id`=表示用/`requestId`=厳密)と役割の対応が逆になっている（`DepositRequest.id`は元々`generateId()`による厳密な一意IDだったため、そちらを変えずに表示用を追加する形にした）。
- ただし**別系統として実装**し、スループット・発行遅延の定数（`DEPOSIT_THROUGHPUT_PER_TICK`等）を引き出し側とは独立して調整できるようにした。処理自体は同じ`system.runInterval`ループの中で、引き出しの処理に続けて呼び出す（`networkProcessing.ts`が両方を束ねる）。
- `DepositRequest`/`DepositLine`自体は引き出しと同様「何を何個」を持てる形にしてあるが、MVPのUIでは検索・カート選択はさせず、**張り付いた先のコンテナに今入っている物を全部まとめて1回のリクエストにするワンボタン**にした（実用上、細かい数量指定のニーズがほぼ無いため）。将来UIを変えたくなってもデータ構造の変更は不要。
- 搬入先(=ネットワーク内のどのストレージに入るか)は、`network.storages`を順番に試し、入りきらない分は次のストレージへ回す（1つのストレージで満杯なら次へ、を全て試して入らなければ「不足」として`wh:deposit_partial`に記録）。
- **既にその品目を持っているストレージへの優先スタッキング**: 素朴に品目ごとに全ストレージを毎回スキャンすると、大規模なネットワーク(例: ラージチェスト30個=1620スロット)で品目数に比例して重くなりすぎる(最悪、1回の預け入れで数万スロット読み取りになり得る)。そのため「どのストレージに何があるか」の索引(`buildStorageIndex`)を**ネットワークごとに1tickにつき1回だけ**作り、そのtick内の全ラインの処理で使い回す。索引はtick開始時点のスナップショットなので、同じtick内で新しく届いた品目までは優先先として反映されないが、次のtickには自然に反映されるため実用上問題ないと判断した。ラージチェスト30個規模で実機検証済み、体感できるパフォーマンス問題は無かった。

### 倉庫の整理: コントローラUIからのワンショットタスクを同じtickループに乗せる

コントローラを(レンチではなく)素手等で右クリックすると`showControllerUi`(`controllerUi.ts`)が開く。「状況」「整理」「設定」の3タブ構成で、タブの選択はターミナルUIと同じく`dropdown`で行う。ドロップダウンの並び順・開いた直後のデフォルトタブのどちらも「状況」(value=0)。「整理」タブは「倉庫の整理」ボタンのみを持つ。押すと、接続されているストレージ群の部分スタックをまとめて空きスロットを増やす処理がキューに積まれる。引き出し/預け入れと同じ「キュー+予算制のtickループ」に乗せることで、実装・永続化・ウォッチドッグ耐性の仕組みを使い回す。

「状況」タブは、進行中の引き出し(`listActiveOrders` = `wh:issuing`+`wh:orders`)・進行中の預け入れ(`listActiveDeposits` = `wh:deposit_issuing`+`wh:deposits`)・進行中の整理(`listActiveOrganize` = `wh:organize`。同時に1件までなので実質0件か1件)を、それぞれ独立したセクション(見出し+ページャー+行ボタン+ページャー、間に`divider`)として上下に並べて表示する。他の一覧UIと同じくROW_COUNT=8のページャー付き。実装本体(`setupCancellableList`/`setupOrderStatusSection`/`setupDepositStatusSection`/`setupOrganizeStatusSection`)は当初`controllerUi.ts`に直接書いていたが、後にターミナルUIにも同じ「状況」タブを追加する際、そのままだと丸ごと重複することになるため`statusListUi.ts`という共通モジュールに切り出した(7章のターミナルUI「状況タブ」参照)。

- **引き出しセクション**: 各行のラベルは「#表示ID 端末名 (プレイヤー名 or 自動発注なら「自動」)」。
- **預け入れセクション**: 引き出しと同じ表示にしてほしいという要望を受け、`DepositRequest`にも`displayId`/`playerName`を追加した(前節参照)ため、引き出しと全く同じ「#表示ID 端末名 (プレイヤー名 or 自動預け入れなら「自動」)」形式で表示する。
- **整理セクション**: `OrganizeLine`は引き出し/預け入れの`OrderLine`/`DepositLine`と違い数量ベースの進捗(`requested`/`delivered`)を持たず、品目ごとの`done`フラグしか無い。また整理には搬入出先のターミナルという概念も無い。そのため表示は品目数ベースの進捗にし、ラベルは「#表示ID 整理(完了品目数/全品目数) (プレイヤー名 or 自動なら「自動」)」、ツールチップも同じ進捗を示すだけの簡潔なものにしている(整理対象はネットワーク全体のカタログなので、引き出し/預け入れのように品目を1行ずつ列挙すると長くなりすぎるため)。整理は自動発注/自動預け入れのような自動トリガーが無く常にプレイヤー操作から始まるが、`OrganizeRequest`自体は`Order`/`DepositRequest`と型を揃えるため`playerName`を持たせてあり、コードは一貫して「空文字列なら自動」という表示ロジックにしている。
- **共通実装**: 引き出しの`OrderLine`と預け入れの`DepositLine`は品目ごとの進捗を全く同じ形(`itemTypeId`/`itemName`/`requested`/`delivered`/`exhausted`)で持つため、一覧・ページャー・キャンセル・ツールチップの生成ロジックは`setupCancellableList<T>`という1つのジェネリック関数にまとめ、引き出し用・預け入れ用それぞれの薄いラッパー(`setupOrderStatusSection`/`setupDepositStatusSection`)から呼び出している。
- **スループット表示とヘッダーの兼用**: 各セクションの一覧の直前に、現在のスループット(処理ループ1回あたりの予算。`ORDER_THROUGHPUT_PER_CYCLE`/`DEPOSIT_THROUGHPUT_PER_CYCLE`/`ORGANIZE_THROUGHPUT_PER_CYCLE`をそれぞれexportして参照。4章「スループット制」参照)を「{引き出し/預け入れ/内部} §7{値}/{サイクルのtick数}tick」(`throughputLabel()`、例:「引き出し 10/20tick」)という固定テキストの`label`で表示する。整理は搬入出先のターミナルを介さずストレージ間でアイテムを動かすだけ(=ネットワーク外部とやり取りする引き出し/預け入れとは性質が違う)なので「内部」と表示している。MVPでは全て固定値でtickごとに変化しないため、値の表示はObservableではなく素の文字列で十分。このラベルは、`setupOrderStatusSection`等が内部で描画するセクション見出し(「引き出し（タップでキャンセル）」等)を兼ねている: 当初は両方を別々に表示していたが、見出しとスループット表示が並んで冗長という指摘を受け、コントローラUIから呼ぶ時だけ`includeHeader`引数(`setupOrderStatusSection`/`setupDepositStatusSection`/`setupOrganizeStatusSection`の最後の引数、デフォルト`true`)を`false`にして、`setupCancellableList`内蔵の見出し行を省略するようにした(ターミナルUI/自動端末UIの「状況」タブはスループット表示自体を持たないため、`includeHeader`は省略してデフォルトの`true`のまま=内蔵の見出しをそのまま使う)。

各行のツールチップには品目ごとの「配送済み/要求数」を色分け(未完了は§e、完了は§a、品切れ確定は§c)して表示する。行をタップするとそのリクエストをキャンセルする(前節「引き出しのキャンセル」参照。預け入れのキャンセルも`cancelDeposit`/`wh:deposit_cancels:<networkId>`/`processDepositCancels`として全く同じ専用優先キュー方式で実装した)。`system.runInterval`でタブ表示中は各セクションの一覧を定期的に自動更新し、`form.show()`(DDUIのCustomFormはプレイヤーが閉じるまで解決しないPromiseを返す)の完了時に両セクション分のタイマーを`system.clearRun`で止めることで、タイマーを残さず安全に自動更新を実現している。更新間隔は当初1秒(20tick)にしていたが、更新のたびにボタンのTooltipが一瞬消えて再表示されチラつく(実機で確認)という指摘を受け、5秒(100tick)に緩めた。

- **リクエストは同時に1件まで**: ボタンを押した時点のネットワーク在庫カタログ(`scanCatalog`)をスナップショットして`OrganizeRequest.lines`(品目ごとに`done`フラグ)を作る。処理中に再度ボタンを押しても、既存のリクエストが終わるまで新規キューイングはしない(`submitOrganize`が`wh:organize:<networkId>`の既存有無を見て弾く)。整理はやり直しても実害が無いワンショット処理なので、複数リクエストを積む意味が無いため。
- **`processNetworkOrganize`**(`organizeProcessing.ts`)は`processNetworkOrders`/`processNetworkDeposits`と並んで同じ`system.runInterval`ループから呼ばれる。未処理の品目(`!line.done`)を1つ取り出し、`ORGANIZE_THROUGHPUT_PER_TICK`(MVP: 十分大きい固定値)の予算内でその品目のスタック整理(`compactKeyInStorages`)を行い、ラインごとに書き戻す。引き出し/預け入れと同様、予算切れなら`done`を立てずに次tickへ持ち越す(退避先の空き不足で行き詰まった場合の扱いは後述)。
- **整理アルゴリズム(`compactKeyInStorages`)**: 呼び出しのたびに対象品目(displayKey一致)が入っている全スロットを`network.storages`の順にスキャンし直し、先頭側(dst)と末尾側(src)からの2ポインタで「dstの空きにsrcの中身を詰める」を繰り返す。専用の再開カーソルは持たず、予算切れで中断しても、次回呼び出し時に現在のコンテナ状態を再スキャンするだけで自然に続きから再開できる(整理は単調に収束する操作なので毎回スキャンし直しても安全)。
- **見た目が同じでも実際には積めない組は無理にマージしない**: displayKey(typeId+nameTag)は「検索UIで区別できない属性は区別しない」という表示上の同一性基準(5章)であり、耐久値やエンチャントなど実際のスタック可否には影響する属性まで無視するわけではない。そのため実際のマージ判定には`ItemStack.isStackableWith`(Minecraft本来のスタック可否判定、耐久値等も見る)を使う。積めない組が見つかった場合はsrcはそのまま維持し、dstだけ進めて別の組み合わせを試す。
- **完了通知**: `submitOrganize`はボタンを押したプレイヤー名(`OrganizeRequest.playerName`、`Order.playerName`と同じ考え方)を記録しておき、リクエストの全ラインが`done`になった時点(`processNetworkOrganize`が`queue`から取り除くのと同じタイミング)で、コントローラの設定タブの「整理完了時に通知する」(コントローラごとの非表示エンティティ`wh:controller_settings`の動的プロパティ、`controllerSettings.ts`。ターミナル設定と同じ発想でネットワーク全体のJSONを肥大化させない)がONなら、ログイン中ならそのプレイヤーに通知する(オフラインなら無視、MVP)。整理には「不足」という概念(引き出しの`shortfall`のような数量の過不足)は無いが、Drain指定ストレージの退避先が足りず一部の品目を諦めて完了扱いにしたケース(前節参照)はありうるため、通知メッセージはその区別を行う: 完了時点で改めてDrain指定ストレージの中に対象品目が残っているか(`anyMatchingItem`)を調べ、残っていれば「一部の品目は整理できませんでした」と付け加える(専用のフラグを持たせず、完了時点の実際の状態から都度判定することで、諦めたラインの検知漏れを防いでいる)。

## 5. アイテム同一性の判定

**原則: 「検索UIの表示で判別できない属性は区別しない」。** 比較関数は表示ロジックから導出する一枚岩の関数にし、カタログのグルーピングにも引き出しの抽出マッチングにも同じ関数を使う。表示と区別の基準がズレることを構造的に防ぐ。

### MVPでの最低限表示

- 標準表示名（`{translate: itemStack.localizationKey}` というRawMessageでクライアント側のlang解決に任せる。自前の翻訳テーブルは持たない）
- カスタム名（銘、`nameTag`）がある場合はそちらを優先表示
- 在庫数

耐久値・エンチャント・lore・旗の模様・本の中身・地図IDなどは**表示しない＝区別しない**（将来、表示要素を追加したらその都度、比較関数にも同じ属性を追加する）。

### 比較関数

```ts
function displayKey(stack: ItemStack): { typeId: string; name?: string } {
  return { typeId: stack.typeId, name: stack.nameTag };
}
```

`typeId`と`nameTag`はどちらも単純な文字列なので、そのままJSON化して`OrderLine`に埋め込める。これにより、複雑な属性をtickをまたいで正確に覚えておくための特別な仕組み（非表示エンティティによる「見本帳」など）は不要と判断し、設計から除外した。将来、表示に出ない複雑な属性（本の中身、地図IDなど）で区別したいという要件が生まれた場合の拡張手段として、アイデアの記録だけ残しておく（8章）。

## 6. ターミナルの実体（設計変更: 非表示バッファエンティティ方式から「張り付いた先のストレージへ直接搬入」方式へ）

当初は、ターミナル自身に9スロットの受け取りバッファを持たせる設計だった。しかし**ブロックには汎用の`minecraft:inventory`コンポーネントが存在しない**（チェスト等のコンテナ機能はエンジンにハードコードされた特別扱いで、データ駆動のカスタムブロック定義に後付けできない。実機検証でも`BP/blocks/*.json`に`minecraft:inventory`を書くと`child 'minecraft:inventory' not valid here`エラーでブロック定義自体がロードされないことを確認済み）ため、非表示・非当たり判定の専用エンティティ（`minecraft:inventory`コンポーネント持ち）をターミナルに紐づけて代用する方式を実装し、スポーン/検索/読み書き/永続化/ブロック破壊時のドロップ/無敵化/意図しない死亡時の自己修復まで**すべて実機検証で正しく動作することを確認していた**（検証内容は本章末尾に記録として残す）。

その後、「ターミナルは右クリックで引き出しUIを開くだけにし、引き出しされたアイテムはターミナルの張り付いた先に置いたストレージへ直接届ける」という方針に変更した。この方式には次の利点がある。

- **非表示エンティティの仕組みが丸ごと不要になる**。搬入先が実在するバニラコンテナになるため、不可視化・無当たり判定・無敵化・自己修復といった対策そのものが要らない（実在のチェストは元々永続化もブロック破壊時のドロップもエンジンが自然に処理する）。
- **引き出し専用UIも不要になる**。プレイヤーは張り付いた先のチェストを普通に右クリックして開けばよく、バニラのドラッグ&ドロップ操作がそのまま使える。
- ターミナルブロック自身は状態を持たない、純粋な「UIの入口」になる。

### 搬入先の解決方法

ターミナルには`minecraft:placement_position`トレイト(`enabled_states: minecraft:block_face`)があり、プレイヤーが設置時にクリックした面がそのままブロックステートの値になる(6方向)。`Order.terminal`(ターミナルの座標)から、処理のたびに動的にこのステートを読み、クリックされた面と逆側の隣接ブロック(=設置の際に支持ブロックとして使われた面)を`getAttachedStorageLocation`(`terminalBlock.ts`)で求め、その`minecraft:inventory`コンポーネントを搬入先として使う。ネットワークへのレンチ接続は不要（ストレージ一覧＝供給元、ターミナルの張り付いた先＝そのターミナル専用の納品先、という役割分担）。張り付いた先にコンテナが無い、または満杯で入らない場合は、既存の「不足」の仕組み（`wh:partial`への記録）にそのまま乗せる。

### (参考記録) 非表示バッファエンティティ方式で実機検証していた内容

現在は不採用だが、得られた知見は将来また同様の課題（ブロックにカスタムの状態を持たせたい）に直面した際の参考として残す。

- ブロックには`minecraft:inventory`が使えないが、**エンティティには正式に存在する**（`container_type`, `inventory_size`等を指定可能。`container_type: "container"`は自動UIオープンなし＝完全にスクリプト制御下）。`entity.getComponent("inventory").container`で`getItem`/`setItem`/`addItem`が使える。
- `minecraft:custom_components`を持つカスタムブロックの`onPlayerInteract`は、通常右クリック/Shift+右クリックの両方で確実に発火し、`event.player.isSneaking`で正しく判別できる（実機確認済み）。
- `dimension.spawnEntity()`でのエンティティ生成、`dimension.getEntities({ type, location, maxDistance })`での再取得、`addItem`/`getItem`の読み書き・スタッキング、ワールド再読み込みをまたいだ永続化を実機確認済み。
- ブロック破壊時は`world.afterEvents.playerBreakBlock`で検知し、対になるエンティティの全スロットを走査して`dimension.spawnItem()`でドロップさせてから`entity.remove()`。`remove()`は「死亡」を経由しない即時除去なので、`minecraft:inventory`の`private`設定に関わらずエンジンは自動ドロップしない(常に自前でドロップ処理が必要)。
- `minecraft:damage_sensor`（`{"triggers": {"deals_damage": "no"}}`）であらゆるダメージを無効化し、通常は`remove()`以外の経路では死なないようにできる(実機確認済み)。
- 保険として`private: false`（死亡時の自動ドロップを有効のまま）にしておき、`world.afterEvents.entityDie`を監視。対応するブロックがまだ存在するなら新しいエンティティを再生成し、死亡時にこぼれた実アイテムを周辺スキャンで回収して詰め直す自己修復を実装・実機確認済み。`EntityDieAfterEvent.deadEntity`はハンドラ内で`location`等が読み取り可能であることも確認できた。

### ターミナルごとのローカル設定（非表示エンティティ方式）

ターミナルごとにローカルな設定（例: 引き出し完了時に通知するか）を持たせたくなった。ブロックが状態を持てない制約は変わらないため、以下の2案を検討した。

1. **(不採用) `network.terminals`(所属情報)に設定を埋め込む** — 一度この形で実装したが、設定を1つ変えるだけでもネットワーク全体のJSON(ストレージ一覧・他のターミナル情報等すべて)を読み書きすることになり、設定項目が増えるほど「所属情報」と「個々の設定」が絡み合って肥大化していく。
2. **(採用) ターミナルごとに専用の非表示エンティティ(`wh:terminal_settings`)を持たせ、そのエンティティの動的プロパティに設定を保存する** — 設定の読み書きがそのターミナル1台分で完結し、`network.terminals`は所属情報(座標)だけのシンプルな`Vector3[]`のまま保てる。設定項目を増やしたくなっても、エンティティに動的プロパティを追加するだけで済み、ネットワーク全体のデータ構造に影響しない。

6章のバッファ用エンティティと同じ仕組み（非表示・無当たり判定・`onPlace`で生成・`onPlayerBreak`で削除）を流用しているが、保持するのは軽量な設定値だけで実物のアイテムは無いため、ドロップ処理や、万一エンティティが失われた際の自己修復のような作り込みはしていない（失われても「設定がデフォルトに戻る」程度の実害で済むため）。事故を減らす目的で`minecraft:damage_sensor`による無敵化だけは入れてある。

**(実機で発見された不具合の修正済み)** 設定エンティティを探す`findSettingsEntity`は`dimension.getEntities({ type, location: centerOf(loc), maxDistance })`で位置検索するが、当初`maxDistance: 2`にしていた。ストレージ用に同じ仕組み（`wh:storage_settings`、Drain機能。3章参照）を作った際、チェストを1ブロック間隔で隣接配置したところ、あるストレージのDrain設定を調べるはずが**1ブロック隣の別のストレージの設定エンティティを誤って拾ってしまう**不具合が発生した（隣接ブロックの中心同士の距離は1.0で、`maxDistance: 2`の範囲に余裕で収まってしまうため）。ターミナルはこれまで密に隣接設置されるケースが無く顕在化していなかっただけで、同じ構造的欠陥を抱えていた。

修正案として、まず`maxDistance`を隣接ブロック中心間の最小距離(1.0)より小さい`0.5`にする案を試したが、「距離のしきい値のチューニングに正しさを依存させる」設計そのものが脆いのではという指摘を受け、より根本的な方式に変更した: **各設定エンティティに、自分がどのブロック座標に属するか(`wh:owner_loc`、`spawnEntity`直後にJSON文字列で書き込む)を自己申告させ、`getEntities`の近傍検索(`maxDistance`はどのみち球状の絞り込みにしか使えず、「その座標そのもの」を厳密取得するAPIが存在しないため必要)で候補を絞り込んだ後、`wh:owner_loc`が要求座標と厳密一致するものだけを採用する**。これにより正しさは距離の数値に依存せず、厳密な座標一致という自明な不変条件だけに依存するようになった。

なお、この修正より前に設置されていたターミナル/ストレージの設定エンティティには`wh:owner_loc`が書き込まれていないため、修正後は「見つからない」扱いになり、次に設定を変更した時点で新しいエンティティが作り直される(名前やDrain指定は一度リセットされ、再設定が必要)。古いエンティティは孤立するが、実害の無い非表示エンティティなので放置してよい(このファイル冒頭で述べている自己修復不要の方針と同じ)。

現在の設定項目:

- `wh:notify_on_complete`（真偽値）: 引き出しの配送完了時に通知するか。デフォルトtrue。
- `wh:name`（文字列）: 通知に表示するターミナル名。設定タブの`textField`からいつでも編集できる。`onPlace`時に`generateTerminalName()`（区別用の仮名。`端末-XXXX`という、引き出しID(素の4桁)とひと目で見分けられる接頭辞付きフォーマット）で自動的に初期値を入れる。
  - (不採用) 金床で銘を付けたアイテムから設置した場合に、その名前を自動で引き継ぐ案も検討したが、`beforeOnPlayerPlace`(プレイヤー情報はあるが位置はまだ確定しない)と`onPlace`(位置は確定するがプレイヤー情報が無い)の間で情報を橋渡しする一時マップが必要になるなど複雑度が見合わないと判断し、設定タブでの手動編集のみに絞った。

## 7. ターミナルUI

UIフレームワークは `@minecraft/server-ui` の新しいリアクティブフォームAPI（Microsoft公式名称「DDUI」、`CustomForm`/`ObservableString`等）を使う。

**MVPではテキストラベルの`CustomForm`のみ**で核となる処理（ネットワークのデータ構造、引き出し処理）を作り切ることを優先する。アイテムアイコン付きグリッド表示（JSON UIによるフォームの見た目上書き。参考: [Chest-UI](https://github.com/Herobrine643928/Chest-UI)。ただし同プロジェクトもインベントリ部分は見た目だけでドラッグ&ドロップは実現していない＝本質的にはクリック駆動のボタンを化粧しているだけ）は、UX向上のための後日の視覚強化として保留する。個人利用アドオンとして将来のMinecraftアップデートとの互換性は考慮しなくてよい、というスタンスなので、この種の手法自体は将来的な採用候補として排除しない。

- **右クリック（Shift問わず）**: 常に引き出しUIを表示する。引き出し操作は張り付いた先のストレージを直接開くことで行うため、専用UIは無い。「引き出し」「預け入れ」「状況」「設定」の4タブ構成（DDUIに専用のタブ部品は無いため、全コントロールに`visible`/`disabled` Observableを付けて出し分けている）。**タブの選択自体は`dropdown`で行う**（当初はボタン3つを並べてトグルする方式だったが、選んだ瞬間に切り替わる方が分かりやすいという要望を受けて変更した。`ObservableNumber`(選択インデックス)の`subscribe`で各タブの`visible`用`ObservableBoolean`に反映している）。
  1. **引き出しタブ**: 開いた瞬間にそのネットワーク内の全ストレージをスキャンし、`displayKey`でグルーピングしたカタログ（サーバー側の一時変数）を作成する。検索用`textField`と共有の数量`slider`（1〜64）で結果を絞り込み、行ボタンでカートに追加、「確定」で`Order`として送信する。確定時、生成された引き出しID（`generateOrderId()`、英数字4桁）をチャットに表示する。絞り込み結果が表示件数（`ROW_COUNT`=8）を超える場合は、一覧の先頭に「現在のページ数 / 全ページ数」のラベルと「▲ 前のページ」・末尾に「▼ 次のページ」ボタンが（前/次ページが実在する時だけ）現れるページャーで送り行き来できる。ページ数ラベル自体も、2ページ以上ある時だけ表示する（1ページしか無いのがほぼ常なので、常時表示すると煩わしいという指摘を受けた。他のページャー付き一覧＝自動端末のウィッシュリスト検索・コントローラの「状況」タブでも同じ扱いにしている）。検索条件を変えた時は1ページ目に戻す。各行のラベルは「{カートに入れた数}/{在庫数} {品名}」の形式で表示し、クリックのたびにそのスロットの表示だけを更新する（下部にまとめてカート内容を表示する`cartLabel`は、この行内表示で確認できるようになったため廃止した）。カートに入れる数量は`Math.min(..., entry.total)`で在庫数を上回らないようにクランプしている。数量スライダーの下に増減モードのトグル（`increaseMode`、初期値ON=増やす/OFF=減らす）があり、OFFの状態で行をクリックすると、指定した数量分だけカートを減らす（0以下になったらカートから除去する。カートに無い品目を減らそうとした場合は何もしない）。トグルのラベル自体も「増やす」「減らす」と状態に応じて動的に変わる（`ObservableString`をトグルの`subscribe`で更新する。単純な文字列を渡すと初期表示のまま固定されてしまうので注意）。
  2. **預け入れタブ**: 8章参照。
  3. **状況タブ**: コントローラUIの「状況」タブ(4章参照)と全く同じ実装(`setupOrderStatusSection`/`setupDepositStatusSection`)を、`statusListUi.ts`という共通モジュールに切り出して両方から使い回している。違いは一覧の絞り込み範囲だけ: コントローラはネットワーク全体が対象なのに対し、ターミナルの「状況」タブは`fetchAll`に渡すクロージャで`locEquals(order.terminal, block.location)`のフィルタを追加し、**この端末が送信元/宛先になっている引き出し・預け入れだけ**を表示する。タブの並び順は「設定」の1つ上（引き出し/預け入れ/状況/設定）で、コントローラの「状況」タブと違い既定タブにはしていない（既定は従来通り引き出しタブのまま）。
  4. **設定タブ**: 6章の「ターミナルごとのローカル設定」参照。現状は「引き出しの配送完了時に通知を表示する」トグルのみ。
  5. **完了通知**: コントローラが引き出しを処理し終えた時点（全ライン`delivered=requested`または`exhausted`確定）で、その設定がONなら、`order.playerName`と同名のログイン中プレイヤーに引き出しIDを含むメッセージを送る（オフラインの場合は何もしない。MVP）。

### 自動端末(`wh:auto_terminal`)

通常のターミナルとは別のブロック。プレイヤーが手動で操作するのではなく、**張り付いた先のストレージを定期的に確認し、事前に設定した「維持したい在庫量」リスト(ウィッシュリスト)に基づいて過不足を自動でネットワークとやり取りする**。ID接頭辞は他と見分けやすいよう`ATM-`。

- **共通化**: 「張り付いた面から搬入先を求める」(`getAttachedStorageLocation`)、「設定エンティティの生成/削除」(`terminalSettings.ts`)、「ターミナルとして扱ってよいブロックか」(`isTerminalLikeBlock`)は通常のターミナルと共通のモジュールを使う。レンチでの接続対象・引き出し/預け入れ処理側の生存確認(`network.terminals`に登録されているか)も、`wh:terminal`/`wh:auto_terminal`のどちらでも同じ扱いになる(預け入れ処理側も当初`wh:terminal`固定で判定していたため、`wh:auto_terminal`からの預け入れがチャンク未読み込み扱いのまま止まってしまう不具合があり、`isTerminalLikeBlock`に統一して修正した)。
- **ウィッシュリスト**: `WishlistLine[]`(品目+目標数)を、通常のターミナル設定と同じ非表示エンティティ(`wh:terminal_settings`)の動的プロパティ(`wh:wishlist`, JSON文字列)に保存する。UIは「自動引き出し」「状況」「設定」の3タブ構成で、**タブの選択は通常のターミナルUIと同じく`dropdown`で行う**(選んだ瞬間に切り替わる)。「自動引き出し」タブは、ネットワークの在庫を検索して目標数を設定/更新する上段と、現在のリストを一覧して削除できる下段の2段構成。
  - 上段は引き出しUIの検索結果一覧と同じ構成に揃えてある: 検索欄・数量スライダー(1〜64)・「増やす/減らす」トグル(状態に応じてラベルのテキスト自体も動的に変わる)・ページャー(「▲ 前のページ」/「▼ 次のページ」、8件を超える場合のみ)。各行は「{現在の目標数}/{在庫数} {品名}」の形式で表示する。ただし**引き出しUIと違い、目標数は在庫数を上回って設定できる**(在庫を将来的に増やしたい、という用途のため上限を設けていない)。「減らす」モードでクリックすると目標数を減らし、0以下になったらリストから除去する(リストに無い品目を減らそうとした場合は何もしない)。
  - 下段(現在のリスト)は1クリックでその品目をリストから削除する(目標0扱いに戻す)点は変わらないが、表示を上段と同じ形式(カスタム名が無ければlocalizationKeyで解決)に揃えた。目標だけ設定されていて現在庫が0の品目は`networkCatalog`のスキャン結果に出てこないことがあるため、カタログ経由ではなく`new ItemStack(line.itemTypeId, 1).localizationKey`のように、typeIdから直接作った(実在庫を必要としない)`ItemStack`から`localizationKey`を取得している。
  - **状況タブ**: 通常のターミナルUIの「状況」タブ(7章)と全く同じ実装(`statusListUi.ts`)を、この端末に絞り込んで使う。自動端末が自動的に発生させる引き出し・自動預け入れ(`playerName`が空文字列)も、他のターミナル発のものと同じ`Order`/`DepositRequest`として同じキューに乗るため、`locEquals(terminal, block.location)`のフィルタだけで自然に対応できた(自動端末専用の特別扱いは不要)。タブの並び順は通常のターミナルUIと同じく「設定」の1つ上で、既定タブにはしていない。
- **定期チェック**: `system.runInterval`による専用ループ(`autoOrderCheck.ts`)を、引き出し/預け入れのtickループとは別に**独立した間隔で**回す。MVPでは固定100tick(5秒)。将来はコントローラ/ターミナルのグレードに応じて可変にする想定（スループット等と同じ考え方）。
  1. **不足分の自動引き出し**: ウィッシュリストの目標を下回っている品目があれば、不足分を引き出しする(従来の「自動引き出し」相当)。
  2. **自動預け入れ**(設定タブのトグル、デフォルトON): ウィッシュリストに無い品目、またはリストの目標を上回っている品目があれば、その超過分(目標に無い品目は全量)をネットワークへ預け入れる。不要なら設定タブで個別に無効化できる。
- **重複送信の防止**: チェック周期ごとに毎回「目標数との差分」を送ると、処理がまだ完了していないうちに次のチェックが走って同じ差分を何度も送ってしまう。そのため、引き出し/発行待ちキュー(`wh:orders`/`wh:issuing`)・預け入れ/発行待ちキュー(`wh:deposits`/`wh:deposit_issuing`)を見て、同じターミナル・同じ品目の未完了ラインが既にあればスキップする(`hasPendingOrderFor`/`hasPendingDepositFor`)。この2関数は元々`autoOrderCheck.ts`にしか無かったが、後述の在庫管理ターミナルの定期チェックからも全く同じ理由で必要になったため、それぞれの対象キューを扱うモジュール(`orderProcessing.ts`/`depositProcessing.ts`)にexportされた形で移し、両方の定期チェックから共有している。
- **通知機能は無い**: 自動発注/自動預け入れには人間の操作が介在せず「誰に通知するか」という宛先概念自体が無いため、設定タブに完了通知トグルは置いていない。当初は`notifyOnComplete`トグルを(常に無効化される前提で)置いていたが、これは「トグルをONにしても実際には一切通知されない」という実機での不具合報告を受けて発覚した設計ミスだった。自動発注は共通の`submitOrder`/`finalizeOrder`(`orderProcessing.ts`)を経由するため、`order.playerName`をダミーの空文字列にして送信しており、`finalizeOrder`側の`world.getPlayers().find(p => p.name === order.playerName)`が常に該当者無しになる(=通知トグルの状態に関わらず無条件で無視される)ことが原因。「送信元プレイヤー」ではなく「直近UIを開いたプレイヤー」等を宛先として新たに記録する代替案も検討したが、ニッチな需要のためにその複雑さを持ち込む価値は無いと判断し、トグル自体を撤去した(預け入れ側はそもそも完了通知の仕組み自体が無い)。
- **手動の引き出し・預け入れUIは無い**: 受け取りは張り付いた先のストレージを直接開けばよく(通常のターミナルと同じ)、手動での引き出し・預け入れ操作もこのターミナル自身は提供しない(用途がウィッシュリストに基づく自動運用に限定されるため)。

### 在庫管理ターミナル(`wh:inventory_terminal`)

自動端末と似ているが、目標の**基準が根本的に違う**第三のターミナル。自動端末は「このターミナルのアタッチ先(張り付いた先のストレージ)に置いておきたい量」を基準にするのに対し、在庫管理ターミナルは**「ネットワーク全体で維持したい在庫数」**を基準にする。例えば「丸石640」と指定すると、ネットワーク全体の丸石在庫が640を超えていれば超過分を引き出してアタッチ先へ退避させ(ネットワーク側を減らす)、640未満ならアタッチ先から不足分を預け入れて補充する(ネットワーク側を増やす)。ID接頭辞は`INV-`。

- **既存資産の再利用が大きい**: 実際にアイテムを動かす手段(`submitOrder`でネットワーク→アタッチ先、`submitDeposit`でアタッチ先→ネットワーク)はどちらも既存のものをそのまま使う。UI側も、自動端末のウィッシュリスト検索結果一覧が元々**ネットワーク全体のカタログ**(`scanCatalog(dimension, network)`)を対象に「目標/在庫数」を表示していたため、在庫管理ターミナルの「目標設定UI」(`inventoryTerminalUi.ts`のsetupStockTargetTab)は`autoTerminalUi.ts`のsetupWishlistTabとほぼ同じ実装をそのまま流用できた(行の意味づけだけが「アタッチ先の目標」から「ネットワークの目標」に変わる)。「状況」タブも他の2種と同じく`statusListUi.ts`をこの端末に絞り込んで使う。
- **新設したデータ**: `WishlistLine`と構造は同じ(品目+目標数)だが意味が違うため、混同を避けて別の型`StockTargetLine`・別の動的プロパティキー(`wh:stock_targets`、`terminalSettings.ts`の`getStockTargets`/`setStockTargets`)として持たせている。
- **定期チェック**(`inventoryCheck.ts`、`startInventoryTerminalCheckLoop`): 自動端末(`autoOrderCheck.ts`)と同じくMVPでは固定100tick(5秒)の専用ループ。品目ごとに「ネットワーク在庫 > 目標」なら引き出しライン、「ネットワーク在庫 < 目標」なら預け入れラインとして集め、それぞれ`submitOrder`/`submitDeposit`にまとめて渡す(1回のチェックで両方向のラインが同時に発生することもある。品目Aは超過、品目Bは不足、ということは普通にありうるため)。重複送信の防止は自動端末と同じ`hasPendingOrderFor`/`hasPendingDepositFor`をそのまま使う。ちょうど目標と一致している(`current === targetAmount`)場合は何もしない安定状態。
  - **ネットワーク全体スキャンのコスト対策**: 自動端末の判定はアタッチ先1個だけのスキャン(`scanContainerCatalog`)で済むが、在庫管理ターミナルは判定にネットワーク全体のスキャン(`scanCatalog`)が要る分コストが高い。そのため、ネットワークにつき**チェック周期ごとに1回だけ**`scanCatalog`し、そのネットワーク内の全在庫管理ターミナルで使い回す(`depositProcessing.ts`の`buildStorageIndex`と同じ、ターミナルごとに舐め直さない設計)。
- **通知トグルは無い**: 自動端末と同じ理由(自動発注/自動預け入れに通知先という概念が無い)。在庫目標に基づく双方向搬送(超過なら引き出し・不足なら預け入れ)自体も常時一体で動く仕様のため、個別に無効化するトグルは無い。
- **自動預け入れ(設定タブのトグル、デフォルトOFF)**: 自動端末の「自動預け入れ」と紛らわしいが対象範囲が違う。在庫管理ターミナルの自動預け入れは**「リストに無い品目がアタッチ先にあれば全量預け入れる」**だけを指す(リストにある品目の扱いは、ON/OFFに関わらず常時有効な在庫目標ロジック側が既に担っている)。デフォルトOFFにしたのは、意図せずアタッチ先の物を全部持っていかれる事故を避けるため(自動端末の対応する設定はデフォルトONなので、ここは意図的に方針を変えている)。動的プロパティは自動端末の`wh:auto_deposit`とは別に`wh:inventory_auto_deposit`を新設した(`terminalSettings.ts`の`getInventoryAutoDeposit`/`setInventoryAutoDeposit`、意味が違うので流用しなかった)。実装(`inventoryCheck.ts`のcheckUnlistedItems)は、アタッチ先のカタログ(`scanContainerCatalog`)を取り、在庫目標リストに載っている品目を除外した上で、残り全量を`submitDeposit`する(自動端末のcheckExcessのうち「リストに無い品目」のケースと同じ考え方)。
- **ブロック定義**: 見た目・当たり判定・設置トレイト(`minecraft:placement_position`、6方向)は自動端末/通常ターミナルと共通のジオメトリ(`geometry.terminal_panel_north`)をそのまま使い、テクスチャの画面部分の色だけ紫系にして見分けている(`BP/blocks/inventory_terminal.json`、`tools/generate-placeholder-icon.mjs`の`inventoryTerminalColorAt`)。`isTerminalLikeBlock`(`terminalBlock.ts`)にも追加し、レンチでの接続対象・引き出し/預け入れ処理側の生存確認のどちらも他の2種と同じ扱いになる。

### 引き出しUIのグリッド化(Chest-UI方式)の検証中(PoC)

もっとも使用頻度が高いUIである引き出しタブを、Chest-UIを参考にしたインベントリ風のアイテムアイコングリッドに作り替えられないか、設計とPoCを進めている。**まだ採否は決まっていない。**

**技術調査で判明したこと**: Chest-UIの実装をソースレベルで確認したところ、以下のような**Mojang非公式・非文書化のBedrock内部挙動**を複数組み合わせて実現していることが分かった。

- グリッド化自体は`ActionFormData`(新しいDDUIの`CustomForm`ではなく、1回のクリックで閉じる旧世代のフォームAPI)のタイトル文字列に`§c§h§e§s§t§...§r`という書式コードだけの目印文字列を仕込み、JSON UI側(`RP/ui/*.json`によるフォーム見た目の上書き)でそれを検知してレイアウトをリスト表示からグリッド表示に切り替える、というハック。
- アイテムアイコンの実描画は、本来ビーコン画面用のコントロールである`beacon.item_renderer`を転用し、Bedrockのレガシーな数値アイテムID(例: `minecraft:diamond` → `306`)を渡すことで行っている。この数値ID対応表(`typeIds.js`)は約2400行、コミュニティによる手動メンテナンスの成果物。
- スタック数・耐久値は、ボタンのラベル文字列先頭に`stack#01dur#00§r`のような目印を仕込み、JSON UI側の文字列演算(`'%.8s' * text`のような、printf書式を利用した部分文字列抽出のハック)で読み取って表示している。

これは本プロジェクトが過去に(二連チェスト判定などで)「非公開の挙動には依存しない」という原則で痛い目を見た反省と真正面から矛盾する。個人利用アドオンなので将来のアップデート互換性は考慮しなくてよいという方針は既にあるが、それとは別に「**そもそも今のゲームバージョンで動くか自体が未検証**」というリスクがある(数値IDベースの仕組みは廃止が進んでいる領域のため)。ユーザーとの相談の結果、視覚的な完成度を優先し、この非文書化の手法をそのまま移植する方針でPoCに進むことにした(安全側の代替案として「グリッドレイアウトのみJSON UIで実現し、アイコンは`ActionFormData.button()`の公式`iconPath`引数(実テクスチャパス)だけで済ませる」案も検討したが不採用)。

**PoCの構成**(`wh:test_chest_ui`アイテム、`chestUiPoc.ts`、`RP/ui/wh_chest_ui.json`):

- Chest-UIの`RP/ui/chest_server_form.json`を土台に、耐久値バー・スロット背景画像・プレイヤー自身のインベントリ表示部分を省いた最小構成に切り詰めて移植した(いずれもテクスチャアセットの追加が必要になるため、まずアイコン+スタック数+クリック検知という核となる仕組みだけを検証する)。
- 名前空間は`chest_ui`のままだと(実際にChest-UIリソースパックを併用した場合に)衝突しうるため`wh_chest_ui`に変更し、目印文字列も`§w§h§c§h§e§s§t§...§r`のように独自プレフィックスを付けた。
- レガシー数値IDは、動作確認用に10品目分だけ`typeIds.js`から転記した(本採用する場合は全品目分の対応表が必要になる。10章「未確定・要検証事項」参照)。
- `wh:test_chest_ui`を(素手同様に)使うと18マスのグリッドが開き、クリックしたスロットの品目をチャットに表示する。

**確認したいこと**: (1) 現在のゲームバージョンで実際にアイコン付きグリッドが正しく描画されるか、(2) クリックしたスロットを正しく検知できるか、(3) フォームを閉じて再表示するループの体感速度(検索のリアルタイム絞り込みを諦める代わりにこの方式を採用する前提のため)。

### 方向転換: 「他アドオンのアイテムが表示できない」問題とPoC第2段階(実在コンテナ方式)

`ActionFormData`のボタンを偽装するグリッド方式(数値ID方式・iconPath方式のどちらも)には、**事前に用意したアイテムごとの対応表に無い品目は正しいアイコンを付けられない**という共通の構造的限界があることが分かった。これは実装の不備ではなく、Chest-UI自身の実装(プレイヤーの実インベントリを表示する時でさえ同じ対応表を経由している)からも裏付けられる。倉庫アドオンの引き出しUIは「他アドオンのアイテムが入っていても正しく機能する」ことが必須要件のため、**この手法のファミリー全体を不採用とする**。

代わりに、**実在のコンテナ(バニラの`minecraft:inventory`)をアイコン描画用のキャンバスとして使う**方式を検証中。ポイントは以下:

- `common.item_renderer`(バニラのUIソース、Mojang公式の`bedrock-samples`リポジトリで確認済み)は`"type": "custom", "renderer": "inventory_item_renderer"`という**エンジンのネイティブなアイテム描画機能**で、`container_items`という、実際に開いたコンテナの中身をエンジンが自動的に反映する収集(コレクション)にバインドされる。対応表を一切経由しないため、どんなアイテム(他アドオン含む)でも常に正しく描画される。
- ただし、この描画が働くのは「プレイヤーが実際にコンテナを開いた瞬間」のみで、`ActionFormData.show()`のようにスクリプトから即座に呼び出す手段は無い(該当するAPIが存在しないことを確認済み)。そのため「引き出しUIを一発で開く」という現在の使用感は諦める必要がある。
- 中身は実在のコンテナなので、スクリプトから自由に`setItem`で書き込める。つまり「本物のチェストの中身をそのまま見せる」のではなく、「本物のコンテナに、ネットワークの在庫を表す代表アイテムを事前に詰めておき、それをプレイヤーに開かせる」という使い方になる(多くのBedrockアドオンの「仮想ショップ」機能と同じ発想)。

**PoC第2段階の構成**(`wh:test_chest_entity`アイテム、`chestEntityPoc.ts`、`BP/entities/test_chest_entity.json`):

- ブロックには`minecraft:inventory`を持たせられない(6章参照)ため、非表示エンティティ(6章で実機検証済みの技術)に`minecraft:inventory`を持たせる。
- `container_type`をバニラのトロッコ+チェスト用の`"minecart_chest"`にすることで、トロッコとしての見た目・挙動を一切持たせずに「右クリックで通常のチェストと同じ27マスUIが開く」ことを狙う(Mojang公式`bedrock-samples`の`chest_minecart.json`で確認したcontainer_typeの値を転用)。
- まだ見た目の上書き(JSON UIでの独自スキン)はしておらず、バニラ標準のチェストUIがそのまま開く想定。アイコン描画の正しさをまず確認するのが目的で、見た目のカスタマイズは次の段階。
- クリック検知は、公式イベント`world.afterEvents.entityContainerOpened`/`entityContainerClosed`(Mojang公式ドキュメントに存在を確認済み)を使い、開いた瞬間と閉じた瞬間のコンテナの中身を比較して差分をチャットに報告する簡易実装。

**確認したいこと**: (1) 独自の非表示エンティティに`container_type: "minecart_chest"`を付けるだけで、トロッコの見た目・挙動を伴わずに右クリックでチェストUIが開くか、(2) 開いたときに表示される10品目のアイコンがすべて正しく表示されるか(対応表を経由しないので、原理的には全品目で正しく表示されるはず)、(3) `entityContainerOpened`/`entityContainerClosed`イベントで開閉と中身の変化を正しく検知できるか。

**実機検証の結果と、実コンテナ方式の不採用。** (1)(3)は動作したが、(2)は当たり判定の小ささ等により右クリックの成否が不安定だった(`has_collision: true`+当たり判定拡大で改善見込み)。しかしそれ以前に、実用面で3つの重大な問題が判明した:

- **手持ちインベントリが一杯だと「取り出す」という選択操作自体が成立しない**。
- **個数の指定ができない**(「丸石を256個引き出し」のような任意の数量を1クリックで表現する自然な手段が無い)。
- **アイテム以外のUI部品(検索テキスト入力・トグル・スライダー)を配置できない**(バニラのコンテナ画面はアイテムスロットの羅列のみ)。

「取り出しを選択の合図にして、閉じた瞬間に回収する」という代替案(実際に他のBedrockアドオンの仮想ショップ機能で使われている手法)も検討したが、上記3つの問題自体は解決しないため、**実コンテナ方式は引き出しUIの主要な操作方式としては不採用とした**。

### PoC第3段階(不採用): `CustomForm`(DDUI)のレイアウト上書き

バニラの`server_form.json`(Mojang公式`bedrock-samples`で確認)には、`ActionFormData`用の`long_form`とは別に`custom_form`という制御があり、これは`ModalFormData`(トグル・スライダー・ドロップダウン等を持つ、リアクティブでない旧世代のフォームAPI)が使うものだと判明した。「`CustomForm`(DDUI)もここを経由していて、表示コントロールの生成方法(`factory`)はそのままに、並べ方(縦一列→密な配置)だけ上書きできるのでは」という仮説を立て、`long_form`の時と同じ「タイトルの目印文字列で分岐する」手法で検証した。

**結果: 仮説は誤りだった。** `CustomForm`のタイトルに目印文字列(書式コードのみで構成)を仕込んでも上書きは発火せず、さらに目印文字列自体が(`ActionFormData`の時と違って)書式コードとして解釈・除去されずにそのまま画面に表示されてしまった。これは`CustomForm`が`ActionFormData`/`ModalFormData`とは異なるテキスト描画経路を使っていることを示しており、`server_form.custom_form`を経由していないと判断できる。`CustomForm`(DDUI)のレイアウトをJSON UI側から上書きする手段は、少なくとも今回発見できなかった。

### PoC第4段階: `ActionFormData`によるアイコン無し・高密度テキストレイアウト

`DDUI`ではレイアウトの自由度(整列・情報密度)が制限されているという指摘を受け、アイコン表示は諦め(対応表問題を丸ごと回避できる)、代わりに`ActionFormData`+`server_form.long_form`の上書き(チェストの実験で機構自体は実証済み)で、**テキストだけの高密度レイアウト**(2列のボタンリスト)を試すことにした。リアクティブ性(ライブ検索・タブ切り替え・閉じずにカート追加)を失うことは既知のトレードオフとして受け入れる前提。

**PoCの構成**(`wh:test_dense_form`アイテム、`denseFormPoc.ts`、`RP/ui/wh_dense_form.json`):

- `wh_chest_ui.json`のグリッド機構(`type: "grid"`+`collection_name: "form_buttons"`)は流用しつつ、アイコン関連のコントロール(`beacon.item_renderer`・`item_icon`)は一切使わず、ボタンごとに`#form_button_text`をそのままラベル表示するだけのシンプルな構成にした。
- `grid_dimensions: [2, 12]`で24品目を2列×12行に配置。ダミーの在庫数付きで24品目を表示するテスト。
- `server_form.json`の`long_form`を3分岐(バニラ標準/チェストグリッド/高密度リスト)に拡張。目印文字列は`§w§h§d§e§n§s§e§r`。

**確認したいこと**: (1) 2列レイアウトが正しく描画されるか、(2) DDUIの1列リストと比べて実際に情報密度が上がっているか(体感)、(3) クリック検知が引き続き正しく動くか。

**実機確認済み**: 2列表示・クリック検知とも正常に動作した。

### PoC第4段階・第2ラウンド: リアクティブ性を失った状態での操作性の検証

見た目の検証ができたので、次に「リアクティブ性(ライブ検索・閉じずにカート追加)を失った状態で、実際の引き出しフロー全体(検索→一覧→数量指定→カートに追加→…→確定)がどこまで実用的に組めるか」を検証する。`ModalFormData`(テキスト入力・スライダーを持つが、送信するまで反映されない旧世代フォーム)と、アイコン無しグリッド表示(`ActionFormData`)を「閉じて再表示」で繋ぎ合わせてシミュレートする。

- **検索**: `ModalFormData`の`textField`でキーワードを尋ね、送信後に絞り込んだ結果をグリッドで表示する(1文字打つごとの絞り込みは無く、送信して初めて反映される)。
- **一覧**: グリッドの先頭2項目を「検索をやり直す」「引き出しを確定する(カート内容表示)」の特殊項目にし、残りを検索結果にする。
- **数量指定**: 品目をクリックすると`ModalFormData`の`slider`(1〜64、前回入力値をデフォルトに)で数量を尋ね、確定するとカートに加算して一覧に戻る。
- **カート**: サーバー側の一時変数(`Record<string, number>`)で保持し、現在のカート内容を一覧のタイトルにも表示する。

この一連の流れが実際に使い物になるか(操作の手数、体感速度、迷いやすさ)を実機で確認したい。

**実機確認の結果、不採用。** 「検索→一覧→数量指定→カート→確定」の一連の操作を試したところ、率直に「今のDDUIより悪い」という評価だった。検索のたびに`ModalFormData`を開き直す手間、数量指定のたびにフォームが切り替わる断続感が、情報密度の向上分を上回るデメリットになると判断された。

**(実機で発見された不具合の修正済み)** 初回実装では、フォームがバニラ標準の縦一列リスト表示のまま(グリッド化されず)、アイコンも市松模様(テクスチャ欠落)になっていた。原因は、`RP/ui/wh_chest_ui.json`にグリッド表示自体の定義は用意していたものの、**それを実際に呼び出す側の上書きファイル(`RP/ui/server_form.json`)を移植し忘れていた**こと。Chest-UI本体は、バニラの`server_form`名前空間の`long_form`コントロール(=`ActionFormData.show()`で実際に表示される画面本体)自体を、タイトルの目印文字列に応じてバニラの縦一列リストを隠し、代わりに`chest_panel`を表示するよう上書きしている。このファイルを`_ui_defs.json`に登録し忘れると、`wh_chest_ui.json`側の定義は一切参照されないため、常にバニラ標準の見た目(市松模様のアイコンを含む)のまま表示される。`RP/ui/server_form.json`を追加し、`§w§h§c§h§e§s§t`という目印文字列で同様に上書きするよう修正した。

**実機検証の結果: レガシー数値アイテムIDから公式`iconPath`方式へ切り替え。** `server_form.json`の修正後、グリッド表示・アイコン描画・クリック検知はいずれも実機で正しく動作することを確認できた。しかし10品目中1品目(`minecraft:apple`、数値ID`880`)だけ、明らかに別のアイテムのアイコンが表示される不具合が実機で見つかった。他の9品目(数値ID3〜523)はすべて正しく表示されており、`beacon.item_renderer`+レガシー数値ID自体の仕組みは今のゲームバージョンでも機能しているが、**`typeIds.js`(コミュニティによる非公式な対応表)の個々のエントリの正確性は品目によっては信用できない**ことが実証された(特に数値IDが大きい品目で起きやすいと推測される。`forms.js`側に`ID < 850`を境に特別な補正を入れている箇所があり、この境界を超えた領域は元々信頼性が低い可能性がある)。

これを受けて、アイコン描画の方式を、`ActionFormData.button(text, iconPath)`の**公式ドキュメントに明記されたiconPath引数**(実テクスチャパスの文字列)を使う方式に切り替えた。`wh_chest_ui.json`側では、`beacon.item_renderer`(非公式)の代わりに、`#form_button_texture`をそのまま画像として表示するだけの単純な`image`コントロール(`item_icon`)に置き換えた。グリッド化の仕組み(`server_form.json`によるバニラ画面の上書き、目印文字列によるレイアウト切り替え)自体は変更していない。数値IDテーブルという継続的なメンテナンスが必要な非公式アセットを丸ごと不要にできる点も利点。ただし、テクスチャパスの命名規則もアイテム(`textures/items/*`、識別子とファイル名が一致することが多く信頼できる)とブロック(`textures/blocks/*`、`oak_planks`→`planks_oak`のようなレガシー命名が残っている場合がある)で信頼度が異なるため、この点も実機での確認待ち。

### 総括: 引き出しUI大幅改修の調査結論

一連のPoC(第1〜4段階、計4方向)を経て、**Chest-UI風のグリッド化・レイアウト刷新は不採用とし、現行のDDUI(`CustomForm`)ベースの引き出しUIを維持する**という結論に至った。各方向性の不採用理由は以下の通り。

1. **`ActionFormData`グリッド+レガシー数値アイテムID**(`beacon.item_renderer`転用): 事前に用意した対応表に無いアイテム(他アドオンのものを含む)は正しいアイコンを付けられない。対応表自体の正確性も実機で疑わしいことが判明した(`minecraft:apple`が誤表示)。
2. **`ActionFormData`グリッド+公式`iconPath`**(実テクスチャパス): 同上の対応表問題が残る。失敗のしかたは「別アイテムに見える」ではなく「市松模様(テクスチャ欠落)」になるだけ安全だが、他アドオンのアイテムを正しく表示できない点は変わらない。
3. **実在コンテナ(非表示エンティティ+`minecraft:inventory`、`container_type: "minecart_chest"`)**: アイコン描画はエンジンのネイティブ機能に任せられるためどんなアイテムでも正しく表示できるが、(a)手持ちインベントリが一杯だと選択操作自体が成立しない、(b)個数指定の自然な手段が無い、(c)検索テキスト入力・トグル等のアイテム以外のUI部品を置けない、という3つの実用上の問題があり不採用。
4. **`ActionFormData`+アイコン無し高密度テキストレイアウト**(`ModalFormData`と繋ぎ合わせ): 見た目(2列レイアウト)は実現できたが、リアクティブ性(ライブ検索・タブ切り替え・閉じずにカート追加)を失った結果、実機での操作性が現行のDDUIより悪いと判断された。

また、`CustomForm`(DDUI)自体をバニラの`server_form.custom_form`(`ModalFormData`用の画面)経由でレイアウト上書きできないか検証したが、`CustomForm`はこの経路を通っていないことが判明し(目印文字列が書式コードとして解釈されず素の文字として表示された)、この案も不成立だった。

**結論として、情報密度の不足は、グリッド化ではなく「ボタンのツールチップを活用する」ことで補う方針とする**(次項参照)。

### DDUIコンポーネント一覧と実機で判明した制約

`@minecraft/server-ui`のDDUI関連APIを一通り確認・実機検証した(`wh:test_ddui_components`)。

**`CustomForm`のコンポーネント**:

| コンポーネント | 用途 | 主なオプション |
|---|---|---|
| `label(text, options?)` | 読み取り専用テキスト | `visible` |
| `header(text, options?)` | セクション見出し | `visible` |
| `button(label, onClick, options?)` | クリック可能なボタン | `tooltip`, `disabled`, `visible` |
| `divider(options?)` | 横罫線区切り | `visible` |
| `spacer(options?)` | 縦方向の空白 | `visible` |
| `textField(label, text: ObservableString, options?)` | テキスト入力 | `description`, `disabled`, `visible` |
| `slider(label, value: ObservableNumber, min, max, options?)` | 数値スライダー | `step`, `description`, `disabled`, `visible` |
| `toggle(label, toggled: ObservableBoolean, options?)` | ON/OFFスイッチ | `description`, `disabled`, `visible` |
| `dropdown(label, value: ObservableNumber, items: DropdownItemData[], options?)` | ドロップダウン選択 | 各項目に`label`/`value`/`description`、全体に`disabled`/`visible` |
| `closeButton()` | 右上×+下部に閉じるボタンを追加 | ー |

`min`/`max`/`step`等は数値だけでなく`ObservableNumber`も渡せ、動的に変更可能。ラベル系の引数はほぼ全て`ObservableString`/`ObservableUIRawMessage`/`string`/`UIRawMessage`を受け付け、Observableを渡すと値が変わるたびに自動更新される。

**`MessageBox`**(このアドオンでは未使用・今回発見): `CustomForm`とは別枠の、`body`+`button1`+`button2`だけのリアクティブな簡易確認ダイアログ。`show()`は`{ closeReason, selection }`を返す。確認ダイアログ(「本当に削除しますか？」等)に使える可能性がある。

**Observable系**: `ObservableString`/`ObservableNumber`/`ObservableBoolean`/`ObservableUIRawMessage`。いずれも`getData()`/`setData()`/`subscribe(callback)`/`unsubscribe(callback)`を持つ。コンストラクタで`{ clientWritable: true }`を渡すとプレイヤー操作による双方向バインディングになる(このアドオンで既に多用している)。`ObservableString`には`getFilteredText(player)`(不適切語フィルタ済みテキストの非同期取得)もある。

**実機で判明した制約(実機で発見された不具合の修正済み)**:

- **プレイヤーが同時に開けるフォームは1つまで**: `CustomForm`が開いたままの状態で別の`MessageBox`/`CustomForm`を`show()`しようとすると`FormVisibilityError`(「既に表示中のフォームを再度表示しようとした」)になる。`CustomForm`はボタンを押しても自動では閉じない(DDUIの「開いたまま更新される」設計のため)ので、別のフォームに切り替えたい場合は明示的に`form.close()`が必要。
- **`close()`の効果はクライアントに伝わるまで数tick必要**: `form.close()`した直後の同一tick内で次のフォームを`show()`すると、依然として失敗することがあった(`FormVisibilityError`と思われる未処理のPromise拒否で、エラーハンドリングを入れていないと症状が「何も起きない」ようにしか見えず原因究明が難しい)。`system.runTimeout(fn, 1)`で1tick遅らせることで解決した。
- **DDUIのメインテキスト(タイトル・ラベル・ボタン本体)は`§`書式コードを解釈しない**: 書式コードがそのまま文字として表示されてしまう(例: `§a`が「§a」という文字列として見える)。これは`CustomForm`のタイトルに目印文字列を仕込んだ際にも確認済みで、`ActionFormData`/`ModalFormData`とは異なるテキスト描画経路を使っていることを示唆している。`UIRawMessage`型にも色を指定する専用プロパティは無い。
- **ボタンの`tooltip`だけは`§`書式コード(色のみ)が効く**: 長文(実機で約300文字)でも省略されずに表示され自動折り返しされる、複数行(`\n`)も使える、行ごとに違う色も指定できる。ただし太字(`§l`)・斜体(`§o`)は効かない(色コードのみ対応)。

**今後の方針**: 情報密度を補いたい箇所には、メインテキストの書式ではなく**ボタンの`tooltip`**を活用する(在庫数・カテゴリ・補足説明等を色分けして詰め込める)。

- コントローラUIの「状況」タブ(4章「引き出し・預け入れ・整理のキャンセル」参照)は、引き出し・預け入れ・整理のいずれにも対応済み。整理のキャンセル単位はリクエスト全体(品目単位のキャンセルは対応していない)。

（Chest-UI方式のグリッドUI化は、4方向のPoCを経て不採用と結論した。7章参照。情報密度はボタンのtooltip活用で補う方針。レンチの汎用設定ツール化(モード切替式)は実装済み。3章参照。）

## 11. 技術メモ

- `@minecraft/server` 2.1.0 / `@minecraft/server-ui` 2.1.0、`min_engine_version` 1.21.0 を使用（プロジェクトに既存設定済み）。
- `ItemStack.isStackableWith(other)`: エンジン自身が「タイプ＋耐久値/エンチャント/名前などのカスタムデータ」を比較して判定するが、**最大スタックサイズが1のアイテム（道具・装備など）には常に`false`を返す**仕様のため、5章の`displayKey`方式ではこれに依存しない。
- `world.getDynamicPropertyTotalByteCount()`で動的プロパティの総バイト数を監視できる。明確な上限は非公開だが、個人利用規模では問題にならない見込み。
- ブロックの`minecraft:block.components`に`minecraft:inventory`は指定不可（6章参照、実機検証済み）。
- **(実機で発見された不具合の修正済み) `minecraft:custom_components`配列は廃止され、カスタムコンポーネントは他の標準コンポーネントと同じように`components`直下へ「フラット化」して書く必要がある(Custom Components V2、`@minecraft/server` 2.0.0以降で強制的に有効)**。このプロジェクトは`@minecraft/server` 2.1.0を使っているため、V1時代の`"components": {"minecraft:custom_components": ["wh:controller"]}`という書き方は無効になり、コンテンツログに`minecraft:custom_components component is not valid from 1.21.90 onward.`エラーと`Block custom component 'wh:controller' is not being used by a block`警告が出て、`onPlace`等が一切発火しなくなる(=コントローラを設置してもネットワークが作られない)という不具合が実機で見つかった。正しい修正は、`minecraft:custom_components`配列そのものを削除し、**そのカスタムコンポーネントのidentifierを`components`直下に直接キーとして追加する**(値は基本的に空オブジェクト`{}`。パラメータを渡したい場合はそこにJSONを書ける)という「フラット化」。例: `"components": {"minecraft:geometry": ..., "wh:controller": {}}`。原因の特定に手間取った経緯: 最初は単純な配置ミス(`components`内→`description`直下→`minecraft:block`直下)を疑い2回試したがどちらも警告が消えず、Web検索で公式ドキュメント(Scripting v2.0.0 Overview「Custom Components V2」の「Flattening」節)を確認して初めて「配置場所ではなく書き方(配列→フラット化)自体が変わった」ことが分かった。ブロック側(`BP/blocks/*.json`)・アイテム側(`BP/items/*.json`、速度/周期/範囲キット・レンチ・テスト用アイテム)の両方を同じ書き方に統一した(ドキュメント上はアイテムも同じ変更の対象だが、コンテンツログではブロック側のみ`[Json][error]`が出ていた)。**さらに、アイテム側の修正だけでは解消しなかった(`Item custom component 'wh:wrench' is not being used by an item`という警告が別途出た)**: `BP/items/*.json`は`format_version`が`"1.21.0"`(一部`"1.21.40"`)のままで、フラット化した書き方がその古いformat_versionでは認識されていなかった。全アイテムJSONの`format_version`をブロック側と同じ`"1.21.100"`に上げて解消した。**教訓**: `minecraft:custom_components`のフラット化は「書き方の変更」であると同時に、対象ファイルの`format_version`が新しい書き方に対応した値になっていることが前提になる。
- **アイテムの説明文(ツールチップの名前下に出るグレーの行)は`ItemStack.setLore()`で動的に付与する**(`itemDescriptions.ts`)。この結論に至るまで2つの不採用案があった。
  1. **(不採用) `ItemStack.setLore()`で所持品変化を監視して動的付与**: 最初の実装。`world.afterEvents.playerInventoryItemChange`(`includeItems`で対象アイテムのtypeIdを絞り込み、`ignoreQuantityChange: true`で個数変化だけの発火を除外)を監視し、対象アイテムでまだLoreが空なら1回だけ`setLore`する方式だったが、**アイテムがプレイヤーの実際の所持品になるまで説明が付かない**(クリエイティブインベントリの一覧パネルで見ている段階では表示されない)という指摘を受けて不採用にした。
  2. **(不採用) アイテム名のlangキーの値自体に`\n`と`§`書式コードを直接埋め込む、完全に静的な方式**: 参照した他アドオン(UtilityCraft)の実装調査で判明した手法(`item.wh:wrench=倉庫レンチ\n§7Shift+右クリックで使用\n\n...`)。`minecraft:display_name`が指すlangキーの値がそのままツールチップとして複数行表示されるためスクリプト不要でクリエイティブ一覧でも即座に表示され、1のLore方式の弱点を解消したかに見えたが、**この値はホットバーでアイテムを切り替えた時に画面上部へ一瞬表示されるポップアップにもそのまま使われる**ため、説明文全体(署名行まで含む)がホットバー切り替えのたびに大きく表示されてしまう不具合が実機で見つかった。「クリエイティブ一覧で見えない」より「毎回のホットバー切り替えで説明文が丸ごと出る」方が実害が大きいと判断し、Lore方式に戻すことにした。
  - **最終的に採用したLore方式は、1と同じ`world.afterEvents.playerInventoryItemChange`監視だが、対象アイテムを速度/周期キットの8種に加えコントローラ・ターミナル系・レンチにも広げてある**。名前(`item.wh:wrench`等)は短いまま変更せず、説明文だけをLoreとして分離して持たせることで、ホットバー切り替えのポップアップには名前だけが表示され、インベントリでのホバー時にのみLoreを含めた詳細が表示される(名前とLoreの表示箇所がBedrock側で明確に分かれているため)。「アイテムがプレイヤーの所持品になるまで説明が付かない」という1の弱点は残るが、個人利用規模の実害としては軽微と判断した。
  - **数値を含む説明文(速度強化キット・周期短縮キットのスループット/処理間隔)は静的な配列ではなく`() => RawMessage[]`という組み立て関数にした**(`ITEM_DESCRIPTIONS`の値は`RawMessage[] | (() => RawMessage[])`)。`getOrderThroughput(tier)`等、実際のテーブル参照関数をLore生成のたびに呼ぶことで、将来スループットのテーブル値を調整してもコード1箇所を直すだけで新規に付与される説明文に反映される(2の静的方式では実現できなかった、ユーザーからの要望)。ただし4章の`giveOrDropKits`等と同じく、**既にLoreが付与済みのスタックは遡って更新されない**。
  - **`RawMessage.with`は`RawMessage[]`ではなく`string[] | RawMessage`(型定義で確認済み)**で、翻訳先の文字列にネストしたRawMessageを渡すには`{ rawtext: [...] }`で包む必要があり、プレースホルダー(`%1$s`等)の構文にも依存する。今回はそれよりも、`RawMessage.rawtext`で書式コードの`{ text: "§9§o" }`とアドオン名の`{ translate: "wh.addon_name" }`を直接連結する方式にした(`ADDON_SIGNATURE_LINE`)。この行専用のlangキーは不要になり、アドオン名を改名したくなった時も`wh.addon_name`という共通の1キーを直すだけで、これを使う全アイテムの説明文に反映される(ユーザーからの要望: 「アドオンの名前を変える可能性が高いので、説明文中に直書きしない」)。
  - ターミナル系(基本/自動/在庫管理)は「概要1行(種別ごとに違う)+使い方1行(共通)」という同じ構造なので、`terminalFamilyLore(summaryKey)`という共通の組み立て関数に概要のlangキーだけを渡して使い回している。
  - 範囲キットの`buildRangeKitLore(tier)`も速度/周期キットと同じ組み立て関数方式(`getRangeForTier(tier)`を都度参照)。ただし`item.wh:range_kit.desc.summary`/`item.wh:range_kit.desc.range`の日本語本文は暫定の仮テキストで、他アイテムと同じく最終的な文面はユーザーが用意する運用のため、確定次第`en_US.lang`/`ja_JP.lang`を差し替える。

## 12. リリース手順(dev/prodパックの分離)

これまで`BP`/`RP`は1組のUUIDだけを持つ単一のパックとして開発していたが、リリース準備として、日常の開発・検証に使う**dev**パックと、実際に使う本番ワールド用の**prod**パックを、**同一のMinecraft環境に共存させられる**ようにした(同一ワールドで同時に有効化することは想定していないため、ブロック/アイテムの名前空間`wh:`はdev/prodで分けていない。UUIDだけを分ければ、Minecraft側は別パックとして正しく扱える)。

- **devパック(`BP`/`RP`)のUUIDは一切変更していない**。既に検証用ワールドに紐付いているUUIDを変えると、そのワールド側で「パックが見つからない」扱いになってしまうため。`header.name`にだけ「(Dev)」を追記し、パック一覧でprodと見分けられるようにした。`mise run install`(既存、変更なし)で今まで通り`development_*_packs`にシンボリックリンクする。
- **prodパックは、devの内容を丸ごとコピーし、`manifest.json`の識別情報(`header.uuid`/`modules[].uuid`/相互の`dependencies[].uuid`/`header.name`)だけ差し替えたビルド生成物**(`tools/build-release.mjs`)。UUIDは`tools/releaseConfig.mjs`に固定値として埋め込んであり、以後変更しない(理由はdevと同じ: 変えると既存のprodワールドとの紐付けが切れるため)。`module`の対応付けは配列の並び順ではなく`type`(`"data"`/`"script"`/`"resources"`)で照合しているため、将来`modules`の順序が変わっても壊れない。
- **`.mcaddon`として生成し、インストールもその`.mcaddon`経由で行う**(`mise run release`→`tools/build-release.mjs`が`dist/StorageNetworkBP.mcpack`・`dist/StorageNetworkRP.mcpack`を作り、その2つをまとめて`dist/StorageNetwork.mcaddon`にする。`mise run install:prod`→`tools/install-prod.mjs`がその`.mcaddon`をOS既定の関連付け(Minecraft)で開く、Windowsの`start`コマンド経由)。dev用の`tools/install.mjs`(シンボリックリンク配置)とは仕組みが根本的に異なるため別スクリプトに分離した。generate-and-symlinkではなくMinecraft本来のインポート経路を実際に通すことで、「配布物として実際にインポートできるか」を自分自身で検証できる。将来他人に`.mcaddon`を配布する可能性を見据えて、この生成物がそのまま配布物になる構成にしてある。
- **zipの生成は外部ライブラリを追加せず自前実装した**(`tools/zip.mjs`)。`package.json`にzip関連の依存が無く、PNG生成(`tools/generate-placeholder-icon.mjs`)も同様にzlib+手組みのチャンク書き込みで自前実装している前例があったため、同じ方針を踏襲した。CRC32のアルゴリズムはPNG生成スクリプトと共通(標準的なpoly `0xEDB88320`のテーブル方式)。圧縮はせず**ストア方式(無圧縮)**にすることで、Deflateエンコーダの実装コストを避けている(Minecraftのインポートは無圧縮でも問題なく読み込める)。`.NET`の`System.IO.Compression.ZipFile`で読み戻して構造とバイト内容が一致することを確認済み。
